# Corsair base image

Resolve paths from the repository root. Use this with `corsair-development` (records, validation) and `corsair-review` (final review); it adds the image-specific steps only and grants no extra authority. Read [SPEC-0007](../../../docs/development/specs/SPEC-0007-openshell-toolchains.md), the [toolchain qualification report](../../../docs/qualification/openshell-toolchains.md) and SPEC-0042 (runtime selection) before starting.

Prerequisites not yet on main when this skill was written: the runtime matrix, its guard test and the requirements report (#48); per-image preparation and the `JAVA` gate table (#51); `TOOLCHAINS`, `PYTHONS` and the pytest version fixtures (#55). Work on a base that has them, stacking on those branches until they merge; never copy their files.

## Rules that do not bend

- **One image per runtime version** (SPEC-0042). Never add a second runtime to an existing image, and never register a nearby version as a substitute: a project that needs JDK 8 is unsupported until a JDK 8 row is qualified.
- **Official upstream base, pinned by digest.** `FROM <registry>/<official image>@sha256:<64 hex>`, the same string in the Dockerfile, in `BASES` and in the matrix row. Record the tag, platform, manifest digest and the upstream Dockerfile source commit in the qualification report.
- **Offline, hash-pinned contents.** Everything the image adds is fetched during trusted preparation and verified: Python wheels by exact URL + SHA-256 (`--no-index --require-hashes`), Maven artifacts against a checked-in expected cache manifest (`m2.sha256`, every JAR/POM hash, reviewed from the first trusted build) that preparation compares to the built cache and fails on any difference. `mvn -C` alone only checks the repository's own checksums and `/opt/corsair-m2.sha256` is an inventory of what arrived, so neither pins anything; the existing `java` and `java8` images still have that gap (IDEA-0002). single downloaded tools by a checked-in `*.sha256` file (`sha256sum -c` in the build). No unpinned `apt`, `pip`, `npm` or `curl | sh`.
- **Image layout.** Fixture project at `/opt/corsair-fixture`, offline caches under `/opt/corsair-*`, `ENV HOME=/tmp`, final `USER 10001:10001`. Anything the sandbox must read is added to the gate's `toolchain_policy` read-only list.
- **Qualification is live.** A Dockerfile, build, trusted control or version string is not qualification. The matrix row is added only after the toolchain gate passed on RIG0 on a fresh kind node, because the detector selects any row present and would route cases to an unqualified image. Until then the PR, plan and `CURRENT.md` say unqualified.
- **Operator-owned.** Pins, the matrix, policies and budgets are never agent-editable and never weakened to get a pass. No blind retries; retain failed attempts in the report.

## Steps

Name the image directory after the runtime version (`python37`, `java8`, `node8`); the existing `python` and `java` directories are the CPython 3.12 and JDK 17 images. Reference walks: `java8` (PR #51, SPEC-0045/PLAN-0049) and `python37` (PR #55, SPEC-0046/PLAN-0050).

1. **Records.** Spec + plan from `docs/development/templates/` (next unused numbers; check open PR branches for collisions with `git ls-tree`). The spec names: the cases the row unblocks (from SPEC-0042's report, `benchmarks/runtime-requirements.md`, from #48), the exact upstream tag/digest, runtime, build tool and framework versions, and what stays unsupported (for example JUnit 4 before 4.12).
2. **Image source** `deploy/qualification/toolchains/<dir>/`:
   - `Dockerfile` starting with the pinned `FROM`, following the closest existing image of the same language line for line, so the diff shows only the version difference.
   - Pin files: `requirements.txt` + `wheels.json` (Python: name, version, filename, url, sha256, one wheel per dependency, Python-tag compatible with the runtime), `pom.xml` with exact plugin versions (Java), `*.sha256` for any single tool such as the JUnit console launcher.
   - A fixture project with the same test shape as its siblings (Java: `corsair.NativeTest` with `nativeRoundtrip` and `nativeRuntime` asserting the image's feature version; Python: `test_native.py`). The fixture uses the framework version the row will claim.
3. **Preparation** `tests/qualification/prepare_toolchains.py`: add `'<dir>': '<base digest>'` to `BASES`; extend `control()` so the trusted control runs the fixture offline (`--network=none`, UID 10001) and asserts test count, names and zero failures/skips; for a Python image, map the directory to its interpreter in `PYTHONS` (wheels are read from that directory's `wheels.json`). Keep per-image `source_hashes(language)` and the `--language` option (from #51 and #55; `PYTHONS` from #55) so adding an image does not invalidate the others' receipts.
4. **Toolchain gate** `tests/qualification/test_toolchains.py`: one gate test per image directory, named exactly `test_native_<dir>_toolchain`, never a shared loop over several images. The full name is the selector: `TOOLCHAINS=<dir>` must select `-k test_native_<dir>_toolchain`, because a bare `-k <dir>` is a substring match (`python` also matches `python37`, and a directory run inside a combined test selects nothing, so pytest exits 5). `TOOLCHAINS` comes from #55, whose Makefile still passes the bare directory, and #51 runs `java8` inside the combined `test_native_python_and_java_toolchains`; both need that change before `TOOLCHAINS=java8` works. Add the image's read-only paths to `toolchain_policy`, and its per-image expectations (javac/runtime version strings, framework's assertion message and engine, as in the `JAVA` table). The gate must cover the same offline diagnostics as the sibling image (missing dependency, no discovery, compilation/collection, assertion) and, where a Corsair runner exists for the language, the runner's own discovery and execution argv on the fixture.
5. **Runtime and framework compatibility.** Corsair code that runs inside the sandbox must load on the new runtime: the runner's command prefix and the witness probe. A feature the runtime lacks (for example `sys.monitoring` before 3.12) is recorded as unsupported in the record and refused as evidence, never a crash and never a pass. Check the runner and report parser offline against real output from each framework version the row will claim (captured fixtures as in `tests/unit/pytest_reports/`, from #55). The qualified range covers only the versions actually run with the runner as is: an exact union such as `==4.12 || ==4.13.2` when only those ran, never a contiguous range across unrun versions and never widened to what a case needs.
6. **Framework support** if the row brings a new test framework or generation: admit it in `src/corsair/agents/environment/frameworks.py`, name it in the `prepare-environment` skill, and add a `frameworks` matrix row whose `versions` set is only what was actually run (exact union, as in step 5). A framework with no Corsair runner and report parser is not a row; record it as a gap.
7. **Matrix row**, added after step 9's gate passes, in `deploy/runtime-matrix.yaml` (from SPEC-0042, PR #48; if the matrix or the preparation changes are not on your base yet, stack on that branch or wait for its merge rather than copying its files): `id` (`<runtime>-<version>-<tool>`), `language`, `base_image` (same digest), `image_source`, `runtime` `{name, version}` with the version measured in the image, `tools` with exact versions, `selector: {}`, and `qualification` `{records, report, note}`. Rows are tried in order; put a row where the first-match rule cannot select it for a requirement another row should own. `tests/configuration/test_runtime_matrix.py` (from #48, relaxed in #51 so a prepared image in `BASES` may precede its row) checks rows against `BASES`, Dockerfiles and cited records.
8. **Offline checks** (cloud or RIG0): `make test-config`; a selection check that a representative build file selects the new row, once the row exists, that an out-of-range version is unsupported with the need named, and that existing rows are still selected for their cases. Where Docker is unavailable, say so; resolving the pins on another runtime is not evidence for this image.
9. **Live on RIG0** (only one thread uses the kind cluster at a time; the holder hands it over with a message to the next session, and project memory records who holds it; worktree under `/home/al/git/corsair/.worktrees/<branch>`, evidence under `.runs`):
   - `make toolchain-images TOOLCHAINS=<dir>` then `make toolchain-images-load TOOLCHAINS=<dir>` (without `TOOLCHAINS`, every image). A retained `.cache/toolchains/<dir>` from an earlier attempt is inspected and archived, never deleted to force a rebuild.
   - `make qualify-toolchain TOOLCHAINS=<dir>` on a fresh admitted node; then one real benchmark case that the row unblocks, on its unchanged build files, through the language's runner in fresh sandboxes at both the vulnerable and fix commits (a per-image target such as `make qualify-python37-case`). An image-only run outside OpenShell is recorded as image-only.
10. **Record the result**: fill the qualification report (artifact table row with tag/digest/source commit, prepared config/manifest digests, run table with JUnit seconds, SDK/command counts, sandbox ids and confirmed cleanup, every failed attempt and its correction), add the matrix row (step 7) with the measured versions, update the plan, `CURRENT.md` (one row per PR; keep all rows on conflict), and SPEC-0042's report if the supported-case count changed. Add a handoff with `corsair-handoff`.

## Review checklist

Same digest in Dockerfile, `BASES` and row; no unpinned fetch; fixture claims only the versions the row claims; gate covers the sibling's diagnostics; row's `runtime.version` is measured, not the tag; no matrix row before a passed gate; in-sandbox Corsair code loads on the runtime; no fallback or version override added anywhere; failed attempts retained.

Do not use this skill to change a project's own versions, to add a package to an image for one case, or to qualify sandbox properties unrelated to the toolchain.
