# Corsair review

Read `AGENTS.md`, the changed files, and the relevant spec/plan/contract. Review the final behavior against the current scope. This is a review checklist, not another required approval meeting or a request to spawn agents.

1. **Purpose and scope:** Does the change satisfy a concrete objective? Are acceptance criteria and exclusions clear? Are unrelated changes or speculative abstractions removable?
2. **Dependencies:** Could the selected SDK/service provide the capability directly? Are new services, shared utilities, agents or repair loops justified by an observed need? Are actual pins/capabilities verified?
3. **Boundaries:** Are ports narrow and vendor objects confined to adapters? Are modes/providers explicit? Does a local change stay local, or are consumers/invalidation rules updated? Is there any silent fallback?
4. **Evidence and security:** Can errors be attributed to the correct layer? Are command delivery and cleanup identity handled correctly? Could a missing endpoint, skipped test, sandbox denial, failed control or invented output produce an unsupported conclusion? Are credentials and trusted records confined?
5. **Unit-test validity across languages/frameworks/CWEs:** Are exactly the control and exploit probes authored and actually executed through existing real application seams on every investigated revision, with native outcomes for both? Does a separate pre-execution review see only source/patch/plan/issue evidence, with its bound result immutable during disposition? Do both probes exercise the intended immutable source and reported condition, with relevant assertions? Reject copied/mocked targets and doubles implementing the guard. Matching observation kinds or differing revision outcomes alone do not establish calibration or source linkage. Do dependency doubles preserve the production logic under test and limit claims to the measured property? Is integration justified by the property? Are optional witnesses behavior-preserving and coverage-bounded? Missing low-level telemetry alone must not reject a valid unit test; a passing generated assertion alone must not admit an unsupported conclusion.
6. **Testing and evaluation:** Do checks exercise changed behavior and required negative paths? For agents, are trajectory/consistency and other relevant dimensions considered with isolated cases and observable metrics? Are fixture, render, live and durable coverage distinguished?
7. **Operations and continuity:** Are latency, calls, tokens, retries and unknown coverage visible where relevant? Are docs, work records, current gate and handoff accurate? Are failure and recovery paths inspectable without additional frameworks?

Record concrete findings with file/record references and impact. Fix authorized findings, rerun affected checks, and update the plan. Report unresolved findings and unavailable checks plainly. Do not turn a checklist into a blanket safety guarantee, prescribe private model reasoning, or require the user to reapprove already authorized work.

For validity-review changes, require cited findings for each probe’s actual production binding, inputs/preconditions, asserted property and substituted dependencies. Derive overall validity from both probes. A copied target is invalid even if identical; a benign input is not an exploit because its test is named one. In evaluations, separate semantic false approvals from contract failures and evaluator defects, preserve old measurements when versioning corrections, and distinguish fixture runner responses from actual generated-test execution.

For the current independent probe pipeline, preserve six roles (environment, identification, planning, control authoring, exploit authoring and assessment), with separate outcome-blind validity and result calls of assessment. Each author sees only its own specification, identity/path, behavior and cited immutable source, writes its own file and returns source-only assertion anchors under its own operator budget. Keep the control an ordinary benign behavior check and the exploit a true reported-condition adversarial safety test. Neither peer drafts nor execution outcomes enter author context. Trusted structural admission does not establish semantic validity; freeze the pair, review both actual source bindings/inputs/assertions/doubles, then require both native outcomes on each revision. Historical joint-author/witness-only measurements remain historical; current split composition does not silently fall back or acquire validity from them. Evaluate each role and both assessment call modes separately across admitted native frameworks, while distinguishing injected host port observations, reviewed native fixtures and live runtime qualification.

For native agent manifests/operator policy, follow the package convention and SPEC-0080/PLAN-0095. Load only fixed trusted package specs with native `AgentSpec.from_file(...)` and `Agent.from_spec(...)`, passing explicit Python capability instances; literal static instructions have one manifest owner, procedure has its skill owner, and Python retains typed contracts, output/current-run validators, restricted tools and native durability. Use explicit operator inference/budget resolution with one profile/ceiling/retry truth and legacy JSON compatibility. Reject repository-controlled manifests, custom capability selectors/settings fields, arbitrary imports and marker verdict protocols. Preserve frozen pre-migration results/histories; check complete instruction/tool/schema/settings/effective-limit parity, then evaluate each migrated role separately with resolved manifest/policy/factory identities. Record missing telemetry and runtime/provider/durable qualification as unknown until actual evidence admits them.

Keep the full agent-package structure. YAML metadata is descriptive config/prompt versions, not capability authority. `factory_identity` is provenance-only; no custom construction helper or SDK-agnostic schema. Current skill loading remains eager; future deferment requires native SDK support and separate scope.
