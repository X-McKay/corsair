# Evaluation gym

The evaluation gym answers one question repeatably: is this change better? It runs a frozen tier of composed cases through the same model route, trusted images and Temporal workflow that production uses, scores every episode on accuracy, evidence, tokens and time, and gates a candidate scorecard against a reference. The design and its work packages are recorded in [PLAN-0003](../plans/active/PLAN-0003-evaluation-gym.md); the improvement wave that drives these commands is the [gym-loop skill](../../.agents/skills/corsair-gym-loop/SKILL.md). Nothing here promotes a baseline or changes what counts as evidence.

Run every command from a synced checkout inside the Nix shell (`nix develop`, then `just sync`). The runner lives in [`entrypoints/gym.py`](../../src/corsair/entrypoints/gym.py); scoring, gate, capture, export and ledger live in [`evaluation/gym/`](../../src/corsair/evaluation/gym/).

## Tiers

Tiers are frozen `corsair.dataset/1` manifests. tier0 and tier1's first 15 rows copy their entries verbatim (same request and oracle paths and digests) from the existing manifests; later tier1 rows and every tier2 row are frozen only through [reviewed intake](#intake-drafting-and-freezing-reviewed-cases):

| Tier | Manifest | Cases | Use |
| --- | --- | --- | --- |
| `tier0` | [gym-tier0.json](../../evals/datasets/gym-tier0.json) | 6: one per language (Python `chain-python-cmdi-b`, and the JavaScript, Ruby, Java, Perl and C chain cases) | Smoke gate; a tier0 REJECTED stops a candidate early, but ACCEPTED needs tier1 |
| `tier1` | [gym-tier1.json](../../evals/datasets/gym-tier1.json) | 21: every runnable composed case (dev 3, safety 2, adversarial 2, chain 8), then reviewed-intake rows in split `chain`: `ih-python-codeinjection-a` and five SecBench.js-pointed JavaScript packages (`sbj-javascript-<package>`) | The acceptance gate |
| `tier2` | [gym-tier2.json](../../evals/datasets/gym-tier2.json) | 4, split `held_out`: JavaScript prototype pollution in SecBench.js-pointed npm packages (`sbj-javascript-<package>`); the accepted packages were sorted by name and alternated between tier1 (odd positions) and tier2 (even), each its own family, trees and licence files imported under [`corpus/secbenchjs/`](../../evals/datasets/corpus/secbenchjs/) | Holdout: run by the orchestrator and the eval auditor only, never by `gym verify` or an experimenter, and never tuned against |

`corsair dataset validate evals/datasets/gym-tier0.json evals/datasets/gym-tier1.json evals/datasets/gym-tier2.json` checks all three. tier2 is the holdout: `gym run tier2` resolves it by name, but the candidate protocol (`gym verify`) runs only tier0 and tier1, experimenter agents never see its per-case results, and a change is never tuned on it. The SecBench.js rows of both tiers were reviewed by the orchestrator pending the owner's audit; each binds the recipe callable by an export name or the `module.exports` marker, and its operator reference pair (control held, exploit polluted, finding line covered) was checked natively in Docker without a model before freezing. Freezing more rows into a tier changes its digest, so the next reading of it needs a new reference run.

Holdout hygiene: a holdout tier is only held out if no family, family stem, chain pair or source tree it uses appears in another split. `just dataset-families evals/datasets/gym-tier0.json evals/datasets/gym-tier1.json evals/datasets/gym-tier2.json` checks the tiers together and exits `1` on a family id or its `<language>/<class>` stem (so bare `xxe` under a Java recipe and `ih-java-xxe` collide), a case, a chain pair in any request layout (`<class>-a`/`<class>-b`, `…/v3/`, `…-v3`) or a source tree (same resolved path, same pair stem directory or same declared digest) that crosses splits; the rules are listed in the [baseline policy](../../evals/baselines/README.md#checking-the-family-grouped-split). A row that shares any of these with tier0 or tier1 belongs in tier1, not the holdout.

## Verify a candidate

`verify` gates tier0 in smoke mode (`--smoke` on `corsair gym gate`): a language regression or a token-ratio breach at tier0 stops the candidate, but the track's improvement criterion is only reported there, because every tier0 language already verifies and its margin is noise; tier1 is gated in full. `--track` and `--target-language` choose the [gate track](#gate-a-candidate) for both tiers (default `objective`); a target language either reference lacks is refused before any tier runs.

The standard candidate protocol is one command:

```bash
just -- gym-verify "<main checkout>/.runs/gym/reference"
corsair gym verify                     # the same, with the default reference
```

`corsair gym verify [--reference DIR] [--repeats 3] [--concurrency 2] [--skip-tier1] [--track objective|accuracy|efficiency] [--target-language L] [--noise FILE …] [--min-cases N] [--budgets FILE] [--temporal-address A]` runs tier0, gates it against `DIR/tier0.json`, and unless that gate is REJECTED runs tier1 and gates it against `DIR/tier1.json`. It prints both gate tables and ends with one line, `VERDICT: ACCEPTED`, `VERDICT: REJECTED`, `VERDICT: INCOMPARABLE` or (only with `--noise`) `VERDICT: INCONCLUSIVE`, exiting 0, 1, 2 or 3. Each `--noise FILE` (repeatable) is a [noise band](#the-noise-band-and-inconclusive) applied to the tier whose reference scored the band's dataset; a band that matches no reference, or two bands for one tier, is refused before any tier runs, and `verdict.json` lists the files under `noise`. `--min-cases N` applies [deciding languages and paired outcomes](#deciding-languages-and-paired-outcomes) to the tier1 gate only (tier0 has one case per language, so every tier0 language keeps deciding its smoke gate); a tier1 reference with no language of N cases, or a target language with fewer, is refused before any tier runs, and the reference run's trajectories are read from `<gym root>/runs/<its run id>/`. That line is also written to stderr in every output format, so a captured log always ends with it while `--format json` keeps stdout one JSON record. The final decision is REJECTED when either gate rejected, else INCOMPARABLE when either gate was incomparable, else INCONCLUSIVE when either gate was inconclusive, else ACCEPTED. `verdict.json` under `<gym root>/verify/<verify-id>/` is one [`VerifyRecord`](../../src/corsair/contracts/gym.py) (schema `corsair.gym-verify/1`): the candidate's `branch` and `commit` (from the runs' scorecards), the gate `track`, the chain `decision`, `tier0` and `tier1` as `TierGate`s (reference scorecard path, candidate scorecard path, run directory and the gate verdict with its reasons, delta J, token ratio and per-language deltas), `skipped` (each tier not run, with `skipped_by_request` or `rejected_at_tier0`), `complete`, the `reference` directory, the sanitized `invocation` and `recorded_at`. `corsair gym ledger append --verdict` reads that file as is (see [Budgets and the ledger](#budgets-and-the-ledger)). `--reference` defaults to `<gym root>/reference` when it exists. `--skip-tier1` stops after tier0; its ACCEPTED is a smoke result, not an acceptance, and `verdict.json` says so (`complete: false`). `verify` holds the [run lock](#the-run-lock) once across both tiers, so no other run lands between them, and takes the same `--lock-timeout` and `--no-lock` switches as `gym run`.

## The shared run store

Gym runs persist in one directory shared by every worktree of the repository, so a run outlives the worktree that produced it and `replay`, `capture` and `runs` see runs from any worktree. The gym root is `<main checkout>/.runs/gym/`, where the main checkout is the parent of `git rev-parse --git-common-dir` (in the main checkout itself this is its own `.runs/gym/`):

| Path | Holds |
| --- | --- |
| `store/` | The content-addressed artifact store of every gym run (`blobs/`, `operations/`) |
| `runs/<run-id>/` | One run directory each (below) |
| `reference/` | The current reference scorecards `tier0.json` and `tier1.json` read by `verify` |
| `verify/<verify-id>/verdict.json` | One record per `verify` |
| `lock/holder.json` | The [run lock](#the-run-lock)'s holder; present exactly while a run or `verify` holds it |
| `lock/queue/<token>.json` | One ticket per run waiting for the lock, removed when it takes the lock, times out or fails |

Settings whose `artifact_root` is not the default `.runs` keep that directory as the store and use `<artifact_root>/gym/` as the gym root; `--out DIR` still places a single run's directory anywhere. Concurrent runs from different worktrees cannot corrupt the store: every blob and operation record is written to a temporary file in its directory, fsynced and published with an atomic `link`, which fails rather than replaces when the name exists; an existing blob has the same content by construction (its name is its sha256), and an existing operation record with different content raises an identity conflict instead of being overwritten. Operation ids are derived from run ids, which carry a time stamp and a random suffix.

`corsair gym runs [--root DIR] [--tier T] [--limit N]` (`just -- gym-runs …`) lists stored runs newest first: run id, commit (`+dirty` when the working tree was; `, changed to <sha7> at finish` when the checkout's commit at the end of the run differs from the one it started at, and `, dirty at finish` when a clean checkout became dirty, see [pinned runs](#pinned-runs-the-dataset-and-the-source)), tier, repeats, sliced, J, macro verified accuracy, worst language, macro effective tokens, p50 seconds, capped-call episodes and run directory; `--format json` prints the same rows. While the run lock is held, the human and Markdown views start with one line naming its holder (run id, tier, branch and commit, pid and host, whether that process still runs, and how long it has held the lock since it took it, or that the held time is unknown for a holder file written before the acquisition time was recorded). It also lists run directories placed directly under the root, the layout before the shared store.

To bring runs made before the shared store into it, copy their run directories and their worktree's store without overwriting anything: `cp -a <worktree>/.runs/gym/<run-id> <gym root>/runs/`, `cp -an <worktree>/.runs/blobs/. <gym root>/store/blobs/`, `cp -an <worktree>/.runs/operations/. <gym root>/store/operations/` (and `cp -a <worktree>/.runs/gym/reference <gym root>/`). Names are content or operation digests, so a name that already exists holds the same record.

### The run lock

Every live run shares one model endpoint, so overlapping runs skew each other's latency and can fail each other's activities (activity heartbeat timeouts under contention are not a property of either candidate). Live runs therefore serialise automatically; there is no marker file to wait for.

- `gym run` and `gym verify` take the lock `<gym root>/lock/holder.json` after the run is admitted (tier, selection, concurrency, `--temporal-address` namespace) and before any image build or Temporal server starts, and release it when the run ends, also when it fails or is interrupted (Ctrl-C). `verify` takes it once for both tiers.
- The holder file records the holder's run id (`verify-…` for a verify), pid, host, branch, commit, tier, `started_at` (when that run started, which may be long before it got the lock) and `acquired_at` (when it took the lock). Every held time (`gym.lock_waiting`, `gym lock status`, the `gym runs` line) counts from `acquired_at`, so a run's own wait is never counted as holding; a holder file without `acquired_at` (written by an older checkout) still reads, and its held time is printed as unknown. It is written whole to a temporary name and published with an atomic `link`, which fails rather than replaces; check, reclaim and publish run under an `flock` on `lock/.guard`, so two waiters cannot both take it.
- Waiters take the lock first come, first served. A caller that finds the lock free and no live waiter queued takes it at once and leaves no ticket. Otherwise it publishes a ticket `lock/queue/<token>.json` (run id, pid, host, tier, branch, commit, token and the time it joined; written whole and published with the same atomic `link` under the same `flock`) and takes the lock only when it is free and no live ticket joined before its own (by join time, then token). It removes its own ticket in the same guarded step that publishes it as holder, and also when it times out or fails (including Ctrl-C); it never removes another waiter's ticket.
- While it waits the caller logs one line, `gym.lock_waiting`, when the wait starts and every 60 s, with the holder's run id and how long it has held the lock (or, when the lock is free, the next earlier waiter), the caller's queue position (`queue position 2 of 3`) and how long it has waited. After `--lock-timeout` (seconds or a duration such as `30m` or `2h`; default `2h`) it exits 2 with a refusal naming the holder or the next earlier waiter; nothing was started.
- A holder whose pid no longer exists on this host is stale: the next caller reclaims it and logs `gym.lock_reclaimed` with the stale holder. A holder on another host is never judged stale, and a pid reused by an unrelated process keeps the lock until `--lock-timeout`; in both cases `corsair gym lock release --force` is the remedy once the holder is known to be gone. Tickets are judged the same way under the guard: a ticket whose pid no longer exists on this host (or that cannot be read) is removed with a `gym.queue_reclaimed` notice, and a ticket from another host is never judged stale; once such a waiter is known to be gone, removing its file under `lock/queue/` is the remedy.
- `run.json` records `lock`: `used`, `holder_run_id` (the run's own id, or the verify id it ran under), `waited`, `wait_seconds`, `waited_for` (each holder it waited for), `reclaimed`, `queue_position` (the 1-based position it joined the queue at; `null` when it took a free lock at its first attempt) and `waiters_ahead` (how many live waiters were ahead of it then). `wall_seconds` starts once the lock is held, so it never includes the wait.
- `corsair gym lock status [--root DIR]` prints the holder (or that the lock is free) and then the queue in the order its waiters will get the lock: run id, tier, pid and host, whether that process still runs, and how long it has waited; `--format json` adds `holder.held_seconds` (`null` when unknown) and a `queue` list. `corsair gym lock release --force [--root DIR]` removes the lock whoever holds it and prints that holder, and refuses (exit 2) without `--force`; it leaves the queue alone, so the waiters still take the lock in the order they joined.
- `--no-lock` exists only for scripted tests: such a run is not serialised with live runs and its timing is not comparable. The lock serialises runs that share a gym root; settings naming another `artifact_root` use that root's lock.

### Intake: drafting and freezing reviewed cases

A holdout tier is filled only through reviewed intake: an agent may draft cases, and only the owner's review decides which oracle is frozen. Two `corsair dataset` commands carry it, with the review sheet between them ([CLI reference](../reference/cli.md#dataset-draft-chain_dir)).

1. The operator writes a recipe template: one admitted `Recipe` member (its `kind` and operator fields) without `module_file` and without the callable (`function`, or `method` for Java), which drafting binds from each directory's `input.json`. The template is operator-owned, like the recipe of any request; no kind is invented, and a kind outside the `Recipe` union is refused. For the Python XXE pair a secret-disclosure template modelled on [`evals/datasets/intake/recipe-read-file.json`](../../evals/datasets/intake/recipe-read-file.json) is:

   ```json
   {"kind": "python.secret_disclosure/1", "payload_parameter": "document", "fixed_kwargs": {},
    "public_files": {"hello.txt": "hello"}, "expected_control": "hello",
    "allowed_exceptions": ["builtins.ValueError"]}
   ```

2. Draft into an ignored directory (never under `evals/`):

   ```bash
   corsair dataset draft evals/datasets/chain/python/xxe-a evals/datasets/chain/python/xxe-b \
     --recipe-template .work/intake/wave1/recipe-python-xxe.json --split held_out \
     --out .work/intake/wave1/draft
   ```

   Each directory becomes `<case id>/request.json` (title, file, line and callable from `input.json` only; `claim_scope` component; source and fixed source admitted in place under `evals/datasets/corpus/` with their snapshot digests) and `<case id>/oracle.proposed.json`, plus `draft.json` (`corsair.dataset-draft/1`, which no dataset loader accepts) and `review.md`. Case ids are `<provenance>-<language>-<directory>` and families `<provenance>-<language>-<class>`, with provenance `ih` (infosec-harness), `pr` (permissive-reduced), `sbj` (SecBench.js-pointed npm material, corpus directory `secbenchjs`), `syn` (a tree beside the chain directory) or `unk` and the language taken from the template's recipe kind (so the C rows filed as `chain/common/c-<class>-<variant>` draft as `ih-c-<class>-<variant>`). The proposal is mechanical: every decisive verdict the kind can reach for a component claim (a clean negative only for a kind with a qualified auditor rubric), no expected verdict, and `expected_fix` `NOT_REQUESTED` unless a fixed source exists. Legacy `expected_label`, `expected_rule` and the case's truth type are copied into the draft as data and never mapped onto the oracle. Drafting reads no `README.md`, `manifest.json`, `submission.json`, `verification/` or legacy narrative, and runs the `dataset validate` checks on every row, listing failures as blockers.

3. The owner reviews `review.md` (a copy is fine) and fills only its last three columns per row: `accept` (freeze the proposal), `amend` (freeze the `oracle.json` they wrote beside the proposal) or `reject`; a reviewer name; and, optionally, the SHA-256 of the oracle file they reviewed. The reviewer may add a last column headed `reason` (header cell `reason`, a `---` cell in the separator row) for why a row was rejected or amended; a sheet without it freezes as before.

4. Freeze:

   ```bash
   corsair dataset freeze .work/intake/wave1/draft --review .work/intake/wave1/review.md \
     --into evals/datasets/gym-tier2.json \
     --against evals/datasets/gym-tier0.json evals/datasets/gym-tier1.json
   ```

   It refuses (exit 2, nothing written) a row without a decision, an edited code-owned cell, a changed draft file, a reviewed digest that does not match, an accepted row that fails the dataset checks, a family, family stem, case, chain pair or source tree (stem or snapshot digest) that sits in another split in `--against` or the existing manifest (each drafted row is checked exactly as `just dataset-families` checks a frozen entry), and more than 64 entries. Otherwise it appends the accepted and amended rows to the manifest (kept entries are unchanged), writes `<case id>.request.json` and `<case id>.oracle.json` in place beside the corpus (`evals/datasets/corpus/`, as for the existing Perl row, because admission refuses `..` in a source path) and exits 1 with the old (`none` for a new manifest) and new dataset digests: a new frozen cohort to review and commit, never a plain success. A manifest outside the evals tree (a scratch rehearsal) keeps absolute, machine-local sources under `<stem>/` and is validated with `--settings` naming that `source_root`.

Freezing changes the tier's digest, so the next gate over it needs a new reference run.

#### Review records and the audit

The sheet stays in the private draft directory, so every complete review is also recorded in the repository. Freeze writes a `corsair.dataset-review/1` record (`DatasetReview`) to `<DIR>/<manifest stem>/<draft id>-<split>.json`, where `DIR` is `reviews/` beside the manifest ([`evals/datasets/reviews/`](../../evals/datasets/reviews/) for the tiers) unless `--record-review DIR` redirects it; the draft id is the draft directory's name, and a timestamp is added rather than overwrite an earlier record. It is written before the manifest is replaced, and also for a review that rejects every row (no manifest change, exit 0); a refused freeze writes none. A record holds the manifest path, the old and new manifest digests, the draft id, the SHA-256 of `draft.json` and of the reviewed sheet, the source root and staged flag, and per drafted row its case id, family, kind, decision, reviewer, reviewed oracle digest, the frozen oracle digest (accepted and amended rows), the `reason` cell, and for a staged row its licence status (`retained` or `NOASSERTION`) and import target. Commit it with the manifest. Paths are relative to the repository; a field that is unknown stays absent, never zero or empty.

```bash
corsair dataset audit evals/datasets/gym-tier0.json evals/datasets/gym-tier1.json evals/datasets/gym-tier2.json
just dataset-audit            # the same, for evals/datasets/gym-tier*.json
```

`dataset audit` lists every manifest row with its latest record (by `recorded_at`, then file name): decision, reviewer and record file. It flags `unreviewed` (no record names the row), `pending_owner_audit` (the reviewer text contains `pending owner audit`, which a stand-in reviewer such as the orchestrator writes), `oracle_changed` (the manifest's oracle digest is not the one the record froze) and `rejected_but_frozen` (the latest record rejected a row the manifest holds), with counts. It always exits 0; `--format json` is the machine output, and the human table prints reviewer names only as short plain text (`hidden` otherwise) and never a reason. `--reviews DIR` reads records from another directory. The rows frozen before the records existed (tier0 and tier1's first 15) read `unreviewed`; the wave-4 c1 and c2 decisions, whose sheets were lost with the agent worktrees, are backfilled as records with `reconstructed: true` and a `reconstructed_from` note, so their 10 rows read `pending_owner_audit` until the owner audits them. No command yet records an owner's audit of an already frozen row: that is a newer record for those rows (same contract, the owner as reviewer) committed beside the earlier one, which the audit then reads as latest.

#### Staged material

Material staged under the private `.work/intake/` tree (a fetched dataset, agent-built chain inputs) is never source of a frozen dataset and nothing is written under `evals/` before the owner's review, so it is drafted with an explicit staging root and imported only at freeze:

```bash
corsair dataset draft .work/intake/batch/chain/case-a .work/intake/batch/chain/case-b \
  --source-root .work/intake --recipe-template .work/intake/batch/recipe.json \
  --split held_out --out .work/intake/batch/draft
```

Every chain directory and every source tree must lie below the staging root, with the usual admission rules applied relative to it (no `..` escape, no symbolic link on the way or inside a tree); the output may not lie under an `evals/datasets` tree. The draft records `source_root` and `staged: true`, each row names its trees below the root, and `review.md` gains two code-owned columns after the source digest: `staged tree` (the source tree, then `fixed` and the fixed tree) and `licence file` (the `LICENSE`, `LICENCE`, `COPYING`, `UNLICENSE` or `NOTICE` files found anywhere in each tree's admitted snapshot, or `none`). Rows drafted this way have provenance `unk` unless the tree sits beside the chain directory (`syn`) or the row's `case.json` `provenance.path` names a known corpus directory (`external/secbenchjs/…` gives `sbj`).

Freeze of a staged draft requires `--import-into`, a directory below the corpus of the manifest's evals tree:

```bash
corsair dataset freeze .work/intake/batch/draft --review .work/intake/batch/review.md \
  --into evals/datasets/gym-tier2.json --import-into evals/datasets/corpus/DIR \
  --against evals/datasets/gym-tier0.json evals/datasets/gym-tier1.json [--allow-noassertion]
```

Before writing anything it re-admits each accepted or amended row's trees against their drafted snapshot digests and refuses (exit 2, nothing written) `import_required` (no `--import-into`), `import_not_staged` (`--import-into` for an unstaged draft), `import_outside_corpus`, `import_target_exists` (`<dir>/<case id>/` exists), `import_source_changed` (a staged tree no longer matches its digest) and `licence_missing` (a tree holds no licence file) unless `--allow-noassertion` is given. It then copies each tree's admitted files byte for byte into `<dir>/<case id>/source/` and `<dir>/<case id>/fixed/` (so every licence and notice file is retained), re-admits each copy against its digest (a mismatch removes everything copied and refuses `import_digest_mismatch`), writes `<dir>/<case id>/provenance.json` (case id, `licence` `retained` or `NOASSERTION`, and per tree its staged path, snapshot digest and licence files), and freezes the rows as above with their sources pointing at the imported trees. Rejected rows are not copied. Licences and notices are the owner's decisions: `NOASSERTION` records that none was found, not that the material may be redistributed.

## Run a tier

```bash
just images-gym                       # optional: build the content-tagged images up front
just -- gym-run tier0 --repeats 3
just -- gym-run tier1 --repeats 3 --concurrency 2
```

`TIER` is a tier name (`tier0` resolves to `evals/datasets/gym-tier0.json`) or a manifest path. Settings default to the checkout's `.state/settings.json` (the live model route) when it exists; pass `--settings FILE` otherwise. Other switches: `--concurrency C` (at most the settings' `max_concurrent_activities`, so no work waits for a slot and skews timing), `--case ID` (repeatable) and `--lang python,c` (sliced runs, see below), `--budgets FILE` (default `evals/experiments/budgets.json` when present), `--out DIR` (default `<gym root>/runs/<run-id>/`), `--run-id ID`, and `--lock-timeout DURATION` and `--no-lock` (see [the run lock](#the-run-lock)).

What the runner does, in order:

1. Reads the manifest once and loads its frozen requests and oracles from those bytes ([pinned](#pinned-runs-the-dataset-and-the-source)), filters entries in memory for `--case`/`--lang` (language is the recipe-kind prefix) and imports every module the end of the run needs. A filtered run is `sliced`: diagnostic only, or a [signal slice](#signal-slices) screened with `gym gate --slice`.
2. Takes the gym root's [run lock](#the-run-lock), waiting while another live run holds it.
3. Tags each language's trusted image by content and builds any missing tag (see [images](#content-addressed-images)).
4. Starts an ephemeral, headless, in-memory `temporal server start-dev` on a free loopback port with the namespace `corsair-gym` pre-created, and waits until it answers. With `--temporal-address A` it instead connects to that server and refuses to run unless the namespace `corsair-gym` already exists there; it never falls back to `default`.
5. Derives an in-memory copy of the settings with namespace `corsair-gym`, task queue `gym-<branch-slug>-<sha7>` (the checkout's branch and commit) and the content-tagged images, composes the production worker in-process with `compose_worker` on that queue, and submits the existing `EvaluationWorkflow` through the typed API. There is no second scheduler or loop.
6. Scores each returned result with the same row scorer as `corsair eval` (`evaluation.scoring.score_batch`) and writes three files in the run directory `<gym root>/runs/<run-id>/`: `report.json` (the `corsair eval` report shape), `trajectories.jsonl` (one scored episode per case and repeat) and `scorecard.json`. Beside them are `run.json`, written when the run starts and completed when it ends (the sanitized command line, git branch, commit and dirty flag, the store and gym root, tier, the manifest path, `dataset_digest`, `dataset_entries` and `dataset_root`, repeats, concurrency, `cases` (the case ids actually run), the `case_filter` and `languages` selection, budgets source and digest, the lock record, start and completion times, wall seconds and episode count, `git_commit_at_finish` and `source_dirty_at_finish`, and the scorecard's `run` context; no settings values or credentials), `dataset.json` (the exact manifest bytes the run was admitted with), `budgets.json` (the exact bytes of the budgets file used, when one was) and the ephemeral server's `temporal.log`. Scoring reads the dataset loaded at admission, never the manifest on disk at the end.
7. Stops the ephemeral server and releases the lock, also when the run fails, and prints the scorecard, the run directory, the store, the transport and the image ids.

The command exits 0 when every row has a stored result and 1 when any row is unavailable (an operational loss, not a measurement). A run that the gym refuses, or that fails before scoring, exits 2 like any other failed command.

### Pinned runs: the dataset and the source

A run executes for an hour against a checkout that must not change under it, and a run that scored itself against whatever manifest sat on disk at the end once reported a 21-row tier's digest, and five unrun cases as failures, for a 16-case run. The gym therefore pins what a run scores:

- Dataset: admission reads the manifest bytes once; the run directory keeps them as `dataset.json`, and `run.json` records their digest (`dataset_digest`, the same digest a report and scorecard record), `dataset_entries`, the `dataset_root` the entries' request and oracle paths resolve against, and `cases`, the ids that ran. The end of the run scores the dataset loaded at admission. `gym verify` reads both tier manifests when it starts.
- Offline reads: `corsair gym score RUN` and `corsair gym capture RUN` read the run directory's `dataset.json` by default (its frozen requests and oracles are still read under `dataset_root` and checked against their digests). `--dataset FILE` is accepted only when its dataset digest equals the pinned one; otherwise the command exits 2 with `dataset_mismatch: --dataset FILE has digest NEW, but run RUN ran the manifest with digest PINNED …` and writes nothing, so a run is never re-scored against another manifest. A `dataset.json` whose digest is not the one `run.json` recorded is refused the same way. `replay` reads only the trajectories and the store, never a manifest.
- Runs from before pinning have no `dataset.json`: `score` still needs `--dataset`, and `capture` takes `--dataset` or the checked-in manifest with the report's digest, as before; both print `Warning: dataset_unpinned: …` on stderr, because nothing can check that manifest against the one the run executed.
- Source: every module the end of the run imports on first use (`FINISH_IMPORTS` in the runner; today the evidence verifier that scoring uses to revalidate saved receipts) is imported at admission, before the lock, images and Temporal, and the `gym run` view's renderer before the run starts, so source merged into the checkout mid-run cannot break the finish with an `ImportError`. A unit test runs `corsair gym run` in a fresh interpreter and fails if any `corsair` module is first imported after Temporal starts.
- Checkout at the finish: `run.json` adds `git_commit_at_finish` and `source_dirty_at_finish` from git, as code-owned as the starting `git` block (`null` when git cannot report them). The scorecard keeps the commit the run started from; `corsair gym runs` marks a run whose commit changed or that became dirty before it finished.

Protocol rule: a live run executes from a checkout that nothing else edits while it runs. The orchestrator runs reference tiers from a detached worktree of the commit under test (`git worktree add --detach .worktrees/gym/ref-<sha> <sha>`, synced with `nix develop -c just sync`), never merges into a worktree that has a live run, and an experimenter does not commit, merge or switch branches in its worktree until its `gym-verify` has printed its `VERDICT:` line. A run marked `changed to … at finish` was not executed from one source; re-run it rather than gate it.

### Content-addressed images

Each language's image is tagged `corsair-<lang>:<tag>`, where `tag` is the first seven hex digits of a sha256 over the sorted relative paths and bytes of the working-tree files in `deploy/<lang>/` and `src/corsair/adapters/sandboxing/drivers/<lang>/` (generated bytecode excluded). Working-tree content, not commits, is hashed, so an uncommitted driver edit gets a new tag. A missing tag is built with the same `docker build -f deploy/<lang>/Dockerfile -t … .` that `just images` uses, so unchanged inputs reuse the cached image and two worktrees never overwrite each other's tags. The run overrides `Settings.images` in memory and records each image id on the scorecard. `just images` keeps the `:0.1` tags for the demo and the documentation.

### Configuration identity

`Settings.identity`, which becomes each result manifest's `config_digest`, excludes the transport and storage fields `temporal_address`, `temporal_namespace`, `task_queue`, `artifact_root` and `source_root`; the scorecard records transport separately. A per-run queue or port therefore keeps the identity, while an image tag (and so any driver or Dockerfile change), a model, a decoding parameter, a limit or an evidence-policy change produces a new one. Results recorded before this change carry the older identity, which included those fields; see the [baseline policy](../../evals/baselines/README.md).

Decoding is part of `config`. `models.decoding` ([configuration](../reference/configuration.md#decoding)) sets `temperature`, `top_p` and `seed` per role or for both; every parameter is unset by default, which sends none and leaves the inference server's sampling defaults, and an unset block is left out of the digest, so every identity recorded before it still matches. Setting any parameter is a new configuration identity on purpose: two runs at different decoding measured different things, and the identity now says which. Without set decoding the server samples at its defaults, which is one source of the run-to-run spread the [noise band](#the-noise-band-and-inconclusive) measures; a reference that changes its decoding needs a new band. Whether production and the gym share one decoding block (for example greedy `temperature: 0` with a fixed `seed`) is the owner's choice; `corsair doctor --model` reports each role's effective decoding and sends it with its probes.

`producer_prompt_digest` and `auditor_prompt_digest` cover only each role's `instructions/system.md`. The code that renders a role's packet (section order, keys, excerpt fitting, the derived-line note, class-reference selection) and the producer's tool declarations is covered by `producer_packet_digest` and `auditor_packet_digest`: `build_manifest` loads each role's frozen probe request from the built package (`corsair/agents/<role>/packet-probe.json`, a `ProducerInput` at round 2 with a previous submission and feedback, and an `AuditInput`; fixed placeholder values, no timestamp, run id, checkout path or settings value), renders it through the live `_producer_prompt`/`_auditor_prompt` and, for the producer, the live toolset's native ADK `FunctionTool` declarations ([`probe_packet_parts`](../../src/corsair/adapters/inference/adk.py)), and records the digest of the ordered parts (`tool.read_file`, `tool.list_files`, `packet`; the auditor has only `packet`). A packet-builder or tool-declaration change therefore gets a new identity even when the instruction, settings and image are unchanged; a change that alters no output for the probe (a branch the probe does not reach) keeps it. The instruction, response schema and any route-added `set_model_response` tool are left to the prompt, output-schema and model components. The tool declarations follow ADK's API variant (`GOOGLE_GENAI_USE_ENTERPRISE`, formerly `GOOGLE_GENAI_USE_VERTEXAI`) and declaration feature flags exactly as the live request does, so compare runs made under the same environment. Manifests recorded before these fields decode them as `null`, and the gate lists `producer_packet` and `auditor_packet` as unknown against such a reference.

## Read a scorecard

`corsair gym score RUN [--dataset MANIFEST] [--out DIR] [--budgets FILE]` rescores a saved report offline into the same two files; `RUN` is a run directory or its `report.json`, and the manifest is the run's [pinned copy](#pinned-runs-the-dataset-and-the-source) (`--dataset` must carry the same digest, and is needed only for a run from before pinning). Its run block comes from the run directory's `run.json`, else from the scorecard beside the report (a run imported without `run.json`, for which `score` then writes one), else from `--run-id`, `--git-commit` and `--git-branch`; otherwise it names only the report and `score` warns on stderr that the run context is unknown. A scorecard records the run (branch, commit, namespace, task queue, concurrency, image ids), the dataset digest, the configuration identities seen, the budgets digest, the models, the repeat count and whether the run was sliced, and summarises per recipe kind and per language:

- Verified accuracy: a case is verified when it passed with a decisive verdict and valid evidence (or passed an oracle that expects an abstention) in more than half of its repeats; the language figure is the mean over its cases, so one flaky repeat in three cannot flip a case. Raw accuracy is the plain pass rate over repeats.
- Reward: 1 for passed and verified, 0 for an unresolved abstention or a [target-side exception](#target-side-exceptions), -0.5 for any other `ERROR` or `UNABLE_TO_RUN`, -1 for a forbidden label or wrong decisive verdict, plus an efficiency bonus (only when verified and usage is known and a budget exists) and small shaping penalties.
- Effective tokens: uncached input + 0.1 × cached input + 4 × output. Unknown usage stays unknown and earns no bonus.
- Seconds: agent seconds plus sandbox host seconds, reported as p50 and p95.
- Failure stops: the gate-ledger stop of each failed episode, counted; a target-side exception counts as `target_exception` instead of its ledger gate `execution_error`, and an unverified round with a recorded INVALID or ERROR role counts under its qualified name (`evidence_unverified:coverage_control`, see [evaluations](../agents/evaluations.md)), also when a report saved before qualified labels is rescored.

The headline `objective_j` is the macro reward plus half the worst language's verified accuracy.

### Reasoning markers

Each trajectory also records where the output budget went, as observations that no reward, verified flag, objective or gate reads: `thought_tokens` (the reported total, `null` when no call reported it), `thought_share` (thought over output tokens), `output_cap` (the per-call cap from the frozen request's `Budget.max_output_tokens`, which `request_digest` binds; results do not carry the budget), `capped_calls` (calls whose reported output reached that cap), `reasoning_cap_exhausted` (a capped call whose thought tokens filled its whole output) and `dominant_call` (position, episode index, output tokens and seconds of the largest call). Per kind and language the scorecard shows the case-mean thought share and the number of episodes with a capped call and with an exhausted cap, and the gate table shows the capped-episode delta per language. The counts stay unknown when a group has no cap or no per-call reports, so a scorecard written before the markers existed shows `unknown` until `corsair gym score` rescores its report. A call counts as capped when its reported output tokens reach the cap; on a route that reports reasoning outside the output count (ADK's native Gemini route) a capped call is not detected.

### Run identity and operational stops

Each trajectory carries `run_identity`, the full [`RunIdentity`](../../src/corsair/contracts/gym.py) read from its stored result's `RunManifest`: package version, configuration identity (`config`), each role's prompt and packet (`producer_packet`, `auditor_packet`; see [configuration identity](#configuration-identity)), agent spec, output schema and runtime skills digests, the risk-assessment and budget-policy digests, the image id and each role's model. The scorecard's `run_identity` keeps every distinct value per component (images and budget policies differ per language and case), so a prompt-, packet- or skill-only change, which leaves `identity_digests` (the configuration identity) unchanged, is still visible. A result without a manifest, or a component an older manifest did not record, stays unknown.

A failed trajectory is `operational`, with an `operational_reason`, when its stop is a fault of the run rather than of the agents. The rule reads only code-owned gate names, the workflow's own timeout reason and the structure of the stored raw receipts, never model text. A recorded role `ERROR` decides first: it is `sandbox_fault` when, in a round that recorded it, the evidence bundle is missing, unreadable or another operation's, or an errored role's raw receipt is missing, unreadable, another operation's or role's, or has no `corsair.driver/1` record (the sandbox adapter's own record, for example `SandboxExecutionError`); otherwise the payload or the target raised (a receipt with a driver record, including a target-side exception or a payload-level `ERROR`), and the episode stays behavioural whatever the ledger says. Only `load_results` reads the receipts, so a caller that passes its own result mapping to `score_report` names no sandbox fault. Without a recorded role `ERROR` the terminal stop decides:

| Reason | Terminal stop in the gate ledger |
| --- | --- |
| `heartbeat_timeout`, `activity_timeout` | `execution_error` whose reason is `<phase>: activity Heartbeat timeout` (or `StartToClose`, `ScheduleToStart`, `ScheduleToClose`) |
| `episode_timeout`, `provider_temporary`, `operation_reconciliation` | the last round stopped at `episode_timeout`, `provider_temporary` or `operation-reconciliation` (a replay refused after an unconfirmed execution, i.e. a lost host) |
| `execution_cancelled` | `execution_cancelled` |
| `evidence_not_run` | the last round has no observation and the workflow ended with an `execution_*` stop |
| `result_unavailable` | the row has no stored result |

`provider_max_tokens`, `packet_too_large`, `provider_permanent`, `producer_abstained`, audit rejects, coverage misses, budget exhaustion and a payload-level `execution_error` stay behavioural. Operational episodes keep their `ERROR` reward and count against verified accuracy and J; this is visibility, not forgiveness. Per kind and language the scorecard counts `operational_episodes`, lists every operational case and repeat under `operational_stops`, and records `verified_accuracy_without_operational_failures`, the majority verified accuracy had each operational episode verified. `render_scorecard` shows the count column and the list.

The gate reports, without changing its decision, an `identity_changes` map (per component: changed, unchanged or unknown) printed as one `Identity changes:` line, and the per-language operational delta. When a regressed language would not regress against the baseline's verified accuracy had its operational episodes verified, the gate stays REJECTED, adds the reason `operationally_confounded` and names the language in `operationally_confounded_languages`, so the orchestrator orders a clean re-run before reading the regression. Identity differences never make a gate INCOMPARABLE.

### Target-side exceptions

The kernel keeps its `ERROR` verdict when a role raises (status `ERROR`, outcome `ERROR`); the gym separates, for its reward only, an exception the target raised from a fault of the harness. A trajectory has `target_exception: true` when its verdict is `ERROR` and every role that the terminal round admitted as `ERROR` has a stored raw receipt (`corsair.raw-evidence/1`, reached through the observation's evidence bundle) that shows a completed native run: a `corsair.driver/1` record for the same operation and role with outcome `ERROR`, junit status `ERROR`, `observation_kind=execution_error`, coverage reported for the recipe module with the bound finding line in `covered_lines`, `cleanup_confirmed`, and no `error` or `driver_error`. The rule reads the raw receipt, not the admitted `RoleObservation`, so it gives the same answer on results stored before and after the verifier keeps coverage on its `ERROR` observations.

Such an episode scores 0, like an abstention: neither a false label nor an infrastructure fault. Its failure stop is `target_exception`, it is never `operational`, and verified accuracy is unchanged (it did not verify). A sandbox fault without a driver record (for example `SandboxExecutionError`), a `driver_error`, an unconfirmed cleanup, an uncovered bound line, a missing or unreadable receipt, a round without an observation, or one errored role that fails the rule keeps the episode at -0.5; a forbidden `ERROR` label still scores -1. Per kind and language the scorecard counts `target_exception_episodes` and lists each case and repeat under `target_exceptions`; `render_scorecard` shows the count column and the list, and `render_gate` the per-language baseline, candidate and delta. A scorecard written before these fields reads them as unknown until `corsair gym score` rescores its report. Only `load_results` reads the receipts, so a caller that passes its own result mapping to `score_report` names no target exception.

## Gate a candidate

```bash
just -- gym-gate "<gym root>/reference/tier0.json" "<gym root>/runs/CAND/scorecard.json"
```

`corsair gym gate --baseline SCORECARD --candidate SCORECARD [--track objective|accuracy|efficiency] [--target-language L] [--smoke] [--noise FILE] [--min-cases N [--root DIR]] [--slice]` prints the decision, the track's rule, its fixed reasons and a metric table, and exits 0 for ACCEPTED, 1 for REJECTED, 2 for INCOMPARABLE and 3 for INCONCLUSIVE (only with [`--noise`](#the-noise-band-and-inconclusive)). `just -- gym-gate BASELINE CANDIDATE` forwards any further switches, such as `--track accuracy`, `--noise FILE` or `--min-cases 3`.

The view lists the baseline's single-case languages (`single_case_languages` on the verdict) and marks a regression in one as `yes (single case)`: with one case, one episode (a target-side exception, say) flips the language between 1.0 and 0.0 and moves J's worst-language term by its whole range, about 0.085 of J on tier1. This is a label only; the reward, J and the decision are unchanged.

A gate decides on one track; the hypothesis's track picks it. Every track first requires that no language's majority verified accuracy fell (`language_regressed`; with `--noise`, below the band's mean, as every delta below then is: see [the noise band](#the-noise-band-and-inconclusive)), and every verdict records its `track`, ΔJ (`delta_j`), the macro verified accuracy delta, the token ratio and the macro p50 seconds ratio, whatever it decided on:

| Track | ACCEPTED also requires | Reasons when it does not hold |
| --- | --- | --- |
| `objective` (default) | `objective_j` gained at least 0.01, and macro effective tokens at most 1.10 × the baseline | `objective_below_threshold`, `tokens_above_ceiling` |
| `accuracy` | macro verified accuracy rose by at least the minimum gain, or the `--target-language`'s verified accuracy rose by at least one case's majority (1 / its cases); and macro effective tokens at most 1.10 × | `accuracy_not_improved`, `tokens_above_ceiling` |
| `efficiency` | macro verified accuracy at least the baseline's, and macro effective tokens or macro p50 seconds at most 0.90 × the baseline | `accuracy_below_baseline`, `efficiency_not_improved` |

The accuracy track's minimum gain is one case's majority flipping in the language with the most cases: macro verified accuracy is the mean over languages of each language's fraction of cases whose majority of repeats verified, so one flip in language L moves it by 1 / (languages × cases of L), and the smallest step is 1 / (languages × the largest language's cases), read from the baseline scorecard's counts. On tier1 (six languages, eleven python cases since c1) that is 1/66 ≈ 0.0152. With no language regressed, any rise is at least that step, and a target language that rose implies macro rose; `--target-language` (accuracy track only, a baseline language) records the hypothesis's target in the verdict. The accuracy track does not decide on J: with one case in each of Ruby, Java, Perl and C, one `ERROR` episode moves J by about 0.085, so J's 0.01 margin is noise for an accuracy change.

On the efficiency track latency counts only when both scorecards record the same `concurrency` and both count zero operational episodes; otherwise the gate adds `latency_not_comparable`, which never rejects by itself, and only the token ratio can qualify. The efficiency track has no token ceiling: a latency gain may spend tokens.

`--smoke` makes a smoke gate for a tier where every language already verifies, so its track's improvement criterion is noise from single flaky episodes: `objective_below_threshold`, `accuracy_not_improved` or `efficiency_not_improved` is still listed among the reasons but does not reject, and only a language regression, the token ceiling, the accuracy floor and the INCOMPARABLE conditions decide. The verdict records `smoke: true` and the view's header reads `Gate (smoke)` (with the track when it is not objective, as in `Gate (smoke, accuracy track)`), so an ACCEPTED smoke gate is never read as an acceptance. `corsair gym verify` gates tier0 in smoke mode.

INCOMPARABLE means the two scorecards answer different questions, so neither a win nor a regression can be read from them: different dataset digests, different budgets digests, a sliced run on either side (gate a sliced candidate with [`--slice`](#signal-slices) instead), fewer than three repeats per case, or unknown token usage. Re-run both sides on the same tier, budgets and repeat count instead of reading the deltas.

### The noise band and INCONCLUSIVE

Two tier1 runs of one configuration at 3 repeats have differed by 0.55 in J and 0.17 in macro verified accuracy, so a gate without a measure of that spread accepts and rejects on noise. The noise band measures it, and a gate given the band refuses to decide on a delta inside it.

```bash
# Two (or more) runs of the reference configuration: run directories or scorecards.
just -- gym-noise "<gym root>/runs/REF-RUN" "<gym root>/runs/REPEAT-RUN"
# Gate against the band; exit 3 is INCONCLUSIVE.
just -- gym-gate "<gym root>/reference/tier1.json" "<gym root>/runs/CAND/scorecard.json" --noise "<gym root>/reference/noise-tier1.json"
just -- gym-verify "<gym root>/reference" --noise "<gym root>/reference/noise-tier1.json"
```

`corsair gym noise RUN RUN [RUN …] [--out FILE] [--root DIR] [--seed N]` reads each run's scorecard (a run directory or a scorecard file; nothing is rescored) and writes one [`NoiseBand`](../../src/corsair/contracts/gym.py) record (schema `corsair.gym-noise/1`) to `--out`, by default `<gym root>/reference/noise-<tier>.json` with the tier from the runs' `run.json` or run ids (runs naming no single tier need `--out`). It refuses, with exit 2 and nothing written, runs the gate could not compare (`dataset_mismatch`, `budgets_mismatch`, `sliced`, `repeats_below_minimum`, `tokens_unknown`), runs whose recorded `run_identity` differs or is unknown (`identity_mismatch`) or whose repeat counts differ (`repeats_mismatch`), fewer than two runs, a run given twice, and an existing `--out` holding a different band (a reference is never replaced; remove it first). The record holds the dataset and budgets digests, repeats, the shared `run_identity`, `n_runs`, the run ids, per metric (objective J, macro verified accuracy, macro effective tokens, macro p50 seconds, and each language's majority verified accuracy) the per-run `values`, `mean`, `half_range` ((max − min) / 2), sample `stdev` and, for tokens and seconds, `max_ratio` (max / min, information only), per run its scorecard's `operational_episodes`, per case the pooled episode counts and the resampled intervals described below. A gate takes the band's mean of each metric from these values; the worst-language and deciding-language means are computed when gating from the per-language values (per run, the lowest or the mean of the named languages' accuracies), so the record carries no further field and a band written before them is read the same way. The view prints the operational episodes per run, every metric per run with the band a gate reads and its resampled interval and mean, the intervals per language set, then the per-case classification and a table of each case's verified episodes per run, its pooled verified / episodes, its majority-pass probability, its stability and, when any were, the operational episodes it left out.

`--noise FILE` on `gym gate` (and `gym verify`, `gym ledger append`) measures each delta from the band's mean and reads it against the band. The installed reference is one of the band's runs, and each of its figures can sit at either end of the band, so a delta from it alone moves with which run was installed: a JavaScript candidate at 4 of 6 has fallen from a reference run at 5 of 6, but not from a band whose runs scored 5, 4 and 3 of 6. With a band, ΔJ, Δ macro and worst-language verified accuracy, each language's Δ majority verified accuracy and, with `--min-cases`, the deciding macro and worst-language figures are measured from the mean of that metric over the band's runs: the verdict records them in `delta_j_to_band`, `delta_macro_verified_accuracy_to_band`, `delta_worst_language_verified_accuracy_to_band`, `language_deltas_to_band`, `deciding_macro_verified_accuracy_to_band` and `deciding_worst_language_to_band` (whose `baseline` is the band's mean). `language_regressed` (a deciding language below its band mean), the accuracy track's steps, the J gain criterion, the efficiency track's accuracy floor, `operationally_confounded` and every within-noise check read these. The deltas from the installed reference keep their fields (`delta_j`, `delta_macro_verified_accuracy`, `language_deltas`, `deciding_macro_verified_accuracy`, `deciding_worst_language`) as information, and the ledger's ΔJ and token ratio columns still read them. A language the band does not record keeps its installed-reference delta (in `language_deltas_to_band` too), and deciding figures over such a language fall back to the installed reference's. On a band without resampled intervals (see below), a difference (ΔJ, Δ macro verified accuracy, the deciding macro accuracy, and a language's Δ verified accuracy when the language is not read by its episodes) lies within noise when its magnitude is at most twice the half-range, the largest difference the band's runs showed, now centred on the band's mean; on a band with them, the candidate's value is read against the interval instead. Token and p50 seconds ratios are taken against the mean of the band's runs: the verdict records `token_ratio_to_band` and `seconds_ratio_to_band` beside `token_ratio` and `seconds_ratio` (against the installed reference scorecard, kept as information), the token ceiling (1.10×) and the efficiency track's 0.90× read the band ratios, and a band ratio lies within noise between the band's min / mean and max / mean. The installed reference is one of the band's runs, and its own tokens can sit at either end of the band, so a candidate's ratio to it alone moves with which run was installed. The verdict records the band (`noise`), the headline metrics within it (`within_noise`) and the languages within it (`languages_within_noise`); the view prints the band, a delta-against-band table, the per-language episode rates (below) and the within-noise list, and its metric table shows both token and p50 seconds ratios, labelled `(installed reference)` and `(band mean)`. The view leads with one sentence saying that its deltas are measured from the band's mean; its metric table puts the `(band mean)` rows (the band's mean, the candidate, the delta) above the installed reference's rows, each labelled `(installed reference)`; its language table shows `Band mean verified` and `Delta (band mean)` before `Installed reference verified` and `Delta (installed reference)`, with `not in band` and a sentence naming any language the band lacks; and the sentences of `language_regressed`, `objective_below_threshold`, `accuracy_not_improved`, `accuracy_below_baseline` and `within_noise` name the band's mean. A verdict recorded before band-mean deltas decodes with them null and empty, and its view reads as it did.

| Case | Without `--noise` | With `--noise` |
| --- | --- | --- |
| Improvement criterion met beyond the band (any track; for efficiency, a band token or seconds ratio below the band's min / mean) | ACCEPTED | ACCEPTED |
| Improvement criterion met, but its delta inside the band (or, for a language read by its episodes, not separated by the exact test) | ACCEPTED | objective track: `objective_below_threshold` within noise, INCONCLUSIVE; accuracy or efficiency track: `accuracy_not_improved` or `efficiency_not_improved`, REJECTED |
| Every deciding reason is a regression (`language_regressed`, `objective_below_threshold`, `accuracy_below_baseline`, `tokens_above_ceiling`) whose metric (each regressed language) lies within noise | REJECTED | INCONCLUSIVE (exit 3), reason `within_noise` added |
| Any regression outside noise, or an unmet accuracy or efficiency criterion | REJECTED | REJECTED |
| A band of another dataset, budgets digest or repeat count | — | INCOMPARABLE, `noise_mismatch` (exit 2) |
| Any INCOMPARABLE condition | INCOMPARABLE | INCOMPARABLE |

Without `--noise` every decision, reason and exit code is exactly as before. A smoke gate still ignores the improvement criterion. The band should come from runs of the baseline's configuration; when the reference changes identity, measure a new band.

Confirmation-run rule: an INCONCLUSIVE gate is neither an acceptance nor a rejection. Run the same candidate commit once more on the same tier and repeats (`just -- gym-run tier1 --repeats 3`) and gate that run against the same reference and band: ACCEPTED or REJECTED decides; a second INCONCLUSIVE is recorded with `--decision inconclusive` and the candidate is not merged. A confirmation run is never pooled with the first run and never added to the band.

Resampled intervals: the half-range of three run values understates the composite metrics' variance. Each case's majority is a coin flip at its pooled episode rate, so a language of 11 cases with majority-pass probabilities 0.26, 0.42, 0.58, 0.74, 0.97, 0, 0, 1, 1, 1 and 1 has an expected majority accuracy near 0.63 with a standard deviation near 0.09, while three runs can sit at 0.455, 0.636 and 0.636 (half-range 0.091). From the same trajectories `gym noise` therefore draws `resamples` synthetic runs (2000) with `random.Random(seed)` (`--seed`, default 0; both recorded in the band): for every case, the band's repeats episodes drawn with replacement from that case's non-operational episodes pooled over the runs, scored by the scorer's own `build_scorecard`. Cases and their episodes are treated as exchangeable within a case and independent across cases; a shared cause across cases in one run (a slow provider hour, say) is not modelled. Per metric (objective J, macro verified accuracy, each language's majority verified accuracy, macro effective tokens and macro p50 seconds) the `NoiseSpread` adds `interval` (`ResampledInterval`: `low` and `high`, the 2.5th and 97.5th nearest-rank percentiles, and the resample `mean`) beside `values`, `mean`, `half_range`, `stdev` and `max_ratio`, which the band-mean deltas still read. `language_sets` (`LanguageSetInterval`) records, for each distinct case count c of the band's languages, the languages with at least c cases (the set `--min-cases c` decides on) and the intervals of their macro and worst-language verified accuracy; the set with c = 1 gives the worst-language interval. A gate given a band with intervals reads J, macro, worst-language, deciding macro and deciding worst-language verified accuracy and each language's majority verified accuracy by the candidate's value: within noise inside [low, high]; a fall (a deciding language below its band mean, the efficiency track's accuracy floor) is outside noise only below `low`; and an improvement (J's gain, the accuracy track's macro and target-language steps) must exceed `high` as well as its minimum step. The deltas reported and stepped stay those from the band's mean. Token and p50 seconds ratios keep the band-mean ratio and its min / mean to max / mean noise (their intervals are information), and the episode-rate tests below are unchanged: a deciding language read by its episodes is decided by Fisher's exact test, and on the accuracy track with such languages the macro criterion still needs a language whose rate rose (the reason sentence says its gain was read by the languages' episodes). The verdict records the rule each metric was read by in `noise_rules` and `language_noise_rules` (`interval`, `half_range`, `band_ratio`, `episode_rate`); the view's delta-against-band table adds the candidate's value, the resampled interval and the rule, and the sentences of `language_regressed`, `objective_below_threshold`, `accuracy_not_improved`, `accuracy_below_baseline` and `within_noise` name the interval and end with the candidate's figures (`J 1.283 (band mean 1.110, resampled interval 0.787 to 1.293)`). A band written before intervals, or without every run's trajectories, has `resamples` and `seed` null and no interval; it keeps the half-range rule, its verdicts record `half_range`, and both views say it carries no resampled intervals. Stored verdicts decode with empty rule maps.

Operational episodes: an episode the scorer flags operational (a heartbeat or activity timeout, a provider error, a sandbox fault; see [run identity and operational stops](#run-identity-and-operational-stops)) is a harness fault, not the configuration's behaviour, so the pooled counts and the resampling leave it out: each `NoiseCase` records `operational_excluded`, and the band records each run's `operational_episodes`. The per-run values and majority outcomes stay the runs as scored. A case with no non-operational episode in one run pools the other runs' episodes; a case with none in any run has no rate, is named in `operational_cases` rather than given a zero rate, and the band then records no resampled interval.

Per-case counts and stability: a language's spread hides which of its cases moved, and one run's majority of three repeats is a coarse unit: a case that verifies one episode in three passes a 3-repeat majority in about 26 % of runs (7/27), so "its majority failed in every run of the band" is not stability. `gym noise` therefore reads each run's `trajectories.jsonl` (beside its scorecard, else `<gym root>/runs/<run id>/`) and records, for every case scored in all runs (`cases`, a list of `NoiseCase`), its majority outcome per run (`majority_verified`, more than half of the run's repeats verified, the same rule as the paired outcomes) and verified episodes per run (`verified_episodes`), its non-operational episodes and verified episodes pooled over the runs (`episodes`, `verified`), and `majority_pass_probability`: with p = verified / episodes, the binomial probability that a run of the band's `repeats` episodes has more than half verified. Its `stability` is `stable_pass` when a majority fail has probability at most 0.05 (1 − the majority-pass probability ≤ 0.05), `stable_fail` when a majority pass has (the probability ≤ 0.05), and `unstable` otherwise. At 3 repeats and three runs (9 episodes) that is 8 or 9 verified for `stable_pass` and 0 or 1 for `stable_fail`. When a run's trajectories are missing or do not reproduce its scorecard, `cases` is null, `cases_unknown` is `trajectories_missing` and `cases_unknown_runs` names the runs, and nothing is guessed. The view counts the classification and lists the unstable and stable-fail case ids. A slice verdict lists its cases the band classifies unstable in `slice_unstable_cases`, and the view prints them, so a sentinel that is a coin-flip is visible; that is reported, never a refusal.

A gate reads these pooled counts with Fisher's exact test, two-sided, on a 2 × 2 table of the candidate's verified and unverified episodes against the band's pooled verified and unverified episodes: p sums the hypergeometric probabilities of every table with the same margins that is no more probable than the observed one, computed exactly ([`evaluation/gym/exact.py`](../../src/corsair/evaluation/gym/exact.py)). The test separates the two rates when p < 0.05. How flips and languages use it is in [the next section](#deciding-languages-and-paired-outcomes).

Older bands: a band written before pooled counts decodes with `episodes`, `verified` and `majority_pass_probability` null on every case (and one written before per-case stability with `cases` null). It is read by the earlier rules: a case's stability follows its per-run majority outcomes (the same in every run, or not), a flip of an `unstable` case, or in a language whose band is a whole case, is within noise (`unstable_case`, `language_band`), and deciding languages are read against their spreads. The noise view and the gate view both say that the band carries no pooled counts. Token and p50 seconds ratios and the deltas are measured from such a band's mean like any band's.

### Deciding languages and paired outcomes

Tier1 has eleven python cases, six JavaScript cases (since c2) and one case each in C, Java, Perl and Ruby. One of the single cases flips between 1.0 and 0.0 across identical runs, so without a floor `language_regressed` fires on it and macro verified accuracy and J move by about 0.17 and 0.5 with no change at all; a candidate whose python fell from 8/11 to 6/11 showed ΔJ +0.46 because Ruby flipped the other way. `--min-cases N` makes the gate decide on what the corpus can support:

```bash
just -- gym-gate "<gym root>/reference/tier1.json" "<gym root>/runs/CAND/scorecard.json" --track accuracy --target-language python --min-cases 3 --noise "<gym root>/reference/noise-tier1.json"
just -- gym-verify "<gym root>/reference" --min-cases 3 --noise "<gym root>/reference/noise-tier1.json"
```

- **Deciding languages.** Only baseline languages with at least N cases (`deciding_languages`) decide `language_regressed`, `accuracy_not_improved` and `accuracy_below_baseline`: the accuracy criteria then read macro verified accuracy over the deciding languages, the minimum gain is one flip in the largest deciding language (1 / (deciding languages × its cases), 1/11 on tier1 at N = 3), a `--target-language` must be a deciding language, and with `--noise` that macro is measured from, and read against, the band's spread of each run's mean of the deciding languages' accuracies (on a band with resampled intervals, against the interval of its `language_sets` entry for exactly those languages, falling back to the spread when it has none) (`deciding_macro_verified_accuracy_to_band`; the deciding worst language likewise, from each run's lowest). The other languages (`reported_languages`) keep their row, labelled `reported only (single case)` or `reported only (<n> cases)` in the Regressed column, and never decide. J, its 0.01 margin, the token ceiling and the noise rules for J and tokens are unchanged: the owner has not redefined J. The verdict reports, beside ΔJ, `deciding_macro_verified_accuracy`, `deciding_worst_language` (the worst deciding language's verified accuracy, J's worst-language term over the deciding languages) and `objective_j_deciding` (J recomputed over the deciding languages, informational), each as baseline, candidate and delta; the view adds them as `Deciding …` rows (with a band, the `(band mean)` rows first).
- **Deciding languages by episode rate.** With a band carrying pooled counts and the candidate's trajectories (which `--min-cases` reads), each deciding language is read by its episodes: the candidate's episodes pooled over the language's cases against the band's pooled episodes of the language's cases, by Fisher's exact test. The verdict records them per language in `language_rates` (`EpisodeRate`: `reference_verified`, `reference_episodes`, `candidate_verified`, `candidate_episodes`, `p_value`), and the view prints them as `Reference episodes`, `Candidate episodes`, `p` and `Within noise`. A deciding language whose majority accuracy fell (`regressed_languages`, `language_regressed`) is a regression outside noise only when its rate is lower and p < 0.05; otherwise it is in `languages_within_noise`, and the gate is INCONCLUSIVE where a within-noise regression made it so before. The accuracy track's criterion counts a language's rise only when its rate is higher and p < 0.05: the macro criterion needs the macro step and a deciding language that rose with a separated rate, and the target criterion needs the target's one-flip step and its own separated rate. The delta-against-band table keeps each language's half-range as information and marks the languages read this way `(episode rate)` in its Within noise column. A language either side has no episodes of, a band without pooled counts, or a gate without the candidate's trajectories reads the language against its spread as before.
- **Paired outcomes.** With `--min-cases` the gate also reads both runs' `trajectories.jsonl` (beside each scorecard, else `<gym root>/runs/<run id>/` for a reference copy; `--root` names another gym root) and compares every case scored on both sides by its majority outcome. `GateVerdict.paired` (a `PairedOutcomes`) counts `pass_to_fail`, `fail_to_pass`, `stable_pass` and `stable_fail`, overall and per language, lists the flipped cases per direction with their language (`PairedCase`: whether the language decides, and whether the flip is within noise and why), names cases only one side scored (`baseline_only`, `candidate_only`; never paired), and counts `deciding_pass_to_fail` and `deciding_fail_to_pass`: flips in deciding languages outside noise. With a band carrying pooled counts, a flip in either direction is outside noise only when Fisher's exact test on the candidate's episodes of that case against the band's pooled episodes of it gives p < 0.05 and the candidate's rate moved in the flip's direction; otherwise it is within noise with `noise_reason` `episode_rate`. Each such `PairedCase` records `reference_verified`, `reference_episodes`, `candidate_verified`, `candidate_episodes` and `p_value`, and the view prints them beside the case (`2/3 vs 3/9 episodes, p 0.523`). Two hand-checked readings: a candidate verifying 3/3 against a pooled 3/9 gives p = 2/11 ≈ 0.18 (noise), and 0/3 against a pooled 9/9 gives p = 1/220 ≈ 0.005 (a flip). A case the band did not record falls back to its language band. With a band without pooled counts, a flip of a case the band classifies `unstable`, or in a language whose band is a whole case (±1.0, a single case that flipped between the band's runs), is within noise (`unstable_case`, which wins when both hold, or `language_band`). The view prints a per-language paired table and the flipped case ids. Trajectories that do not reproduce their scorecard's per-language case counts and majority accuracy are not used; when none are found the gate warns on stderr, records `paired: null` and the view says the paired outcomes are unknown.
- **`paired_regression`.** On the accuracy or objective track, a gate that would otherwise be ACCEPTED is REJECTED with `paired_regression` when `deciding_pass_to_fail` exceeds `deciding_fail_to_pass`. Without a band, with one dataset on both sides a deciding language whose majority accuracy did not fall cannot lose more cases than it gained, so a deciding language fell and `language_regressed` already keeps the gate from accepting (REJECTED, or INCONCLUSIVE inside noise): `paired_regression` fires only when the trajectories given to `gate()` disagree with the scorecards, which the CLI and `verify` never pass (they use only trajectories that reproduce their scorecard). With a band, `language_regressed` reads each language from the band's mean while the paired outcomes still pair the installed reference's cases, so a deciding language that fell from the installed reference but not from the band's mean can lose more cases than it gained; `paired_regression` then rejects only when those flips are outside noise. It is a guard on the per-case record; the paired table is the reading aid.

Use `--min-cases 3` for every tier1 gate of the loop (with the reference band), so a single flaky case is shown but cannot accept or reject a candidate; read a single-case language's flip in the paired list as one episode. Do not use it on tier0, where every language has one case (the gate refuses: no language has three cases). Without `--min-cases` every decision, reason, view and ledger cell is exactly as before; a verdict recorded before the option decodes with `min_cases` 1 and no paired outcomes, and one recorded before pooled counts decodes with empty `language_rates`, null band ratios and null episode counts on each `PairedCase`. The ledger's gate cell lists `paired_regression` like any other reason.

### Signal slices

A tier1 run costs about an hour of the live route, and most of its 21 cases are irrelevant to any one hypothesis: an effect on two or three cases disappears under flips elsewhere. A signal slice runs only the cases the hypothesis targets and screens them on their paired per-case outcomes before the full run is spent.

- **The slice.** Per hypothesis: its target cases (stable failures it means to fix, from the auditor's brief) plus two stable-pass sentinel cases of the same language as regression canaries. Run it with five repeats, so each case's majority rests on more episodes than the reference's three: `just -- gym-run tier1 --repeats 5 --case TARGET --case SENTINEL-1 --case SENTINEL-2`. The run is recorded `sliced` (its scorecard's `repeats` reads 0, the fewest repeats over the whole dataset; the gate counts the slice's repeats from its trajectories).
- **The screen.** `corsair gym gate --baseline "<gym root>/reference/tier1.json" --candidate "<gym root>/runs/SLICE/scorecard.json" --slice [--noise "<gym root>/reference/noise-tier1.json"] [--root DIR]` (`just -- gym-gate BASELINE CANDIDATE --slice …`; `gate(..., slice=True)` in Python) gates the sliced candidate against an unsliced baseline, or one sliced to exactly the same cases, on the candidate's cases only. It reads both runs' `trajectories.jsonl` as `--min-cases` does (beside each scorecard, else `<gym root>/runs/<run id>/`) and refuses (exit 2) when either is missing or does not reproduce its scorecard, and with `--smoke`, `--track` other than objective, `--target-language` or `--min-cases`, none of which applies. It decides only on the paired majority outcomes of the slice cases (`paired`, a `PairedOutcomes` restricted to the slice): REJECTED with `slice_regressed` when any slice case went from pass to fail outside the noise band, REJECTED with `slice_not_improved` when no slice case went from fail to pass outside it, otherwise ACCEPTED. With `--noise`, a flip within noise counts neither way: with a band carrying pooled counts, each slice case's flip is read by Fisher's exact test on the candidate's episodes (five per case) against the band's pooled episodes of that case, exactly as in a full gate; with a band without them, a flip in a language whose band is a whole case (±1.0) or of a case the band classifies unstable is within noise, so a single-case target cannot pass a screen read against such a band. The slice's token and seconds ratios are over the slice and have no band ratio. INCOMPARABLE (exit 2): different dataset or budgets digests, fewer than three repeats on either side over the slice, a band of another dataset, budgets or baseline repeat count (the slice itself may run five), and `slice_mismatch` (a candidate case the baseline did not score, a sliced baseline of other cases, or no case at all). Token usage unknown on either side does not make a slice incomparable.
- **What the verdict reports.** `GateVerdict.slice` is true, `slice_cases` lists the candidate's cases and `slice_repeats` the fewest repeats the candidate ran of them. ΔJ, the macro verified accuracy delta, the token and p50 seconds ratios and the per-language deltas are recomputed over the slice cases on both sides and reported; none of them decides, and `regressed_languages` stays empty. The view's header reads `Gate (slice)`, says the result is a slice screen and not an acceptance, prints `Slice: <n> cases × <repeats> repeats` with the case ids, shows the metric and language tables over the slice (Regressed column `not decided (slice)`) and the paired table, in which every slice case decides.
- **Then the full run.** A hypothesis whose screen is ACCEPTED goes on to the full tier1 run and gate with `--min-cases 3 --noise …` (`just -- gym-verify "<gym root>/reference" --min-cases 3 --noise …`), which alone can accept it. A screen never merges anything. REJECTED stops the hypothesis at the cost of one slice run; INCOMPARABLE means the slice was not run as a slice of the reference (fix the cases or repeats and re-run it).

Without `--slice` a sliced scorecard stays INCOMPARABLE (`sliced`) exactly as before, and a verdict recorded before slices decodes with `slice` false. The ledger records a screen in its own `slice` field (`gym ledger append --slice RUN-DIR`, see [the ledger](#budgets-and-the-ledger)).

## Replay, capture and export

`replay`, `capture` and `score` read results from the store the run directory's `run.json` names, else from the configured or shared store.

- `just -- gym-replay RUN-DIR CASE` (`corsair gym replay RUN-DIR --case ID`) prints each repeat's round timeline (stop, payload digest, abstention, audit decision and rule, role outcomes, sandbox seconds), the per-call tokens, tool result sizes and seconds from the stored usage, and the code-owned explanation of the verdict. It never prints payloads, hypotheses or model reasons; JSON output carries the same fields.
- `just -- gym-capture RUN-DIR CASE [--reference RUN-DIR …]` freezes every failed repeat of a case as agent fixtures and datasets under `evals/` and kernel replay cases under `tests/replay/kernel/`. The manifest is the run directory's [pinned copy](#pinned-runs-the-dataset-and-the-source) (`--dataset` must carry the same digest); a run from before pinning uses `--dataset` or the checked-in manifest with the report's dataset digest, with a warning. A reference run over the same dataset may supply the demonstrated payloads for a case that flipped to failing.
- `corsair gym export-grpo --runs RUN-DIR … --out FILE` writes grouped rewards and group-normalised advantages with per-round proposals and identity digests; packets and reasoning are never written.

## Budgets and the ledger

- `corsair gym budgets --from SCORECARD --out FILE` derives per-kind token and time budgets from a scorecard's p95 values and prints their digest. Both sides of a gate must use the same budgets file.
- `just -- gym-ledger append --id ID --entry baseline|experiment [--wave N] [--track …] [--idea …] [--lesson …] …` appends one row to `evals/experiments/ledger.jsonl` ([`LedgerRow`](../../src/corsair/contracts/gym.py)). A row's `branch` and `commit` always name the candidate; every source that names them (`--branch`/`--commit`, the scorecards, a verify record) must agree, and a short commit agrees with its full form.
  - Baseline: `--scorecard S --tier T` records the scorecard's headline metrics. A baseline without a scorecard is refused.
  - Experiment with gates: `--tier0 RUN-DIR|SCORECARD` and `--tier1 RUN-DIR|SCORECARD` gate each candidate against `--reference-tier0`/`--reference-tier1` (a ledger row id or a scorecard path; default the latest baseline row of that tier) and record the reference, the scorecard, the run directory (when a directory was given) and the gate verdict with its ΔJ, token ratio and per-language deltas. `--verdict FILE` instead copies both tier gates and the candidate identity from a [`VerifyRecord`](../../src/corsair/contracts/gym.py), normally the `verdict.json` that `corsair gym verify` wrote (`just -- gym-ledger append --id ID --entry experiment --wave N --verdict <gym root>/verify/<verify-id>/verdict.json --decision …`); a tier the record did not run stays absent (`—`), and it cannot be combined with `--tier0`/`--tier1`. `--scorecard S --tier T --baseline REFERENCE` still gates a single scorecard. `--noise FILE` (repeatable) applies each band to the gates whose reference scored its dataset (refused when it matches none, or with `--verdict`) and records the files in the row's `noise`; a `--verdict` row copies the verify record's `noise`.
  - Slice screen: `--slice RUN-DIR|SCORECARD` gates a [signal-slice](#signal-slices) run with `gate(..., slice=True)` against `--reference-tier1` (default the latest tier1 baseline row; `--reference-tier1` is accepted with `--slice` alone) and records it in the row's `slice` field (a `TierGate`), reading both runs' trajectories (`--root DIR` names the gym root for a reference copy's). `--noise` bands apply to it as to the tier1 gate. It can be combined with `--tier1`, not with `--verdict`. A row whose only gate is a slice screen cannot record `--decision accepted` or `merged`: a screen is never an acceptance.
  - Experiment without a scorecard (an offline dx change): `--branch B --commit C` alone.
  - `--decision accepted|rejected|inconclusive|merged` records the orchestrator's decision; `merged` requires `--merge-commit SHA`, and only `merged` takes one.
  - Touched files: an experiment row records `touched_files`, the sorted repository-relative files its candidate changed, from git in the current checkout: `git merge-base HEAD <commit>`, or for a `--merge-commit` row `git merge-base <merge commit>^1 <commit>` (HEAD already contains a merged candidate), then `git diff --name-only --no-renames` from that base to the commit, so a rename lists both paths. A commit the checkout cannot resolve records an empty list and logs one `gym.ledger_files_unresolved` notice; the row is still appended. `--touched-files PATH …` records the given paths instead and skips git. A baseline records none. Rows recorded before the field read as an empty list.
  - Refusals exit 2 with a fixed message and leave the ledger unchanged: an existing id, a baseline without a scorecard, a merged decision without its merge commit, disagreeing candidate identities, `--reference-tierN` without `--tierN` (or, for tier1, `--slice`), `--slice` with `--verdict`, an accepted or merged decision on a slice screen alone.
- `just -- gym-ledger render` regenerates the tables of `evals/experiments/LEDGER.md` below its hand-written header (everything above `## Baselines` is kept byte for byte). The Waves table shows, per experiment, id, track, `branch@commit`, the tier0 and tier1 gate (decision, including INCONCLUSIVE, reason codes, regressed languages and, for a gate given a band, the metrics and languages within noise), ΔJ and token ratio as `tier0 / tier1`, the decision (with the merge commit) and the lesson; `—` marks a value the row does not record. A row's slice screen leads its tier1 cell as `slice: <gate> (<n> cases × <repeats>)` (followed by `; <tier1 gate>` when the row also has one) and the rejected-ideas summary; its ΔJ and token ratio are never shown. Rows without a slice render exactly as before. A wave table gains a Files column after `branch@commit` once one of its experiments records touched files: the first two paths, then `+N` for the rest, `—` for a row without any; a wave with none renders as before. The rejected-ideas table lists rows whose decision is `rejected`. Lesson and idea text is printed as given on one line with pipes escaped; the contract bounds it at 500 and 300 characters.
- `just -- gym-ledger constraints --files PATH … [--limit N] [--ledger FILE]` prints the constraints for a brief that will touch those paths: under the heading `## Prior rejected experiments on these files` and a sentence that none may be repeated unless the brief explains what differs, the most recent `N` (default 5, newest first in ledger order) experiments decided `rejected` or `inconclusive` whose touched files include a given file or lie under a given directory (`src/corsair/agents/producer` matches every file below it; `./` and a trailing `/` are dropped, an absolute path inside the checkout is made relative). Each shows its id, wave, decision, `branch@commit`, idea, its tier1 gate cell led by any slice screen (else its tier0 gate), the matching files and its lesson. With no match it prints one line saying so; either way it names how many such experiments record no touched files and so cannot be matched, and exits 0. `--format json` emits the matching rows. The text is the orchestrator's own ledger text and gate codes, so it may be pasted into a brief.
- `just -- gym-ledger backfill [--write] [--ledger FILE] [--markdown FILE]` resolves touched files, as `append` does, for every experiment row that records none, and prints per row its id, commit and file count with the first paths, or that the commit is not resolvable in this checkout, then a summary. It changes nothing without `--write`. With `--write` it replaces the ledger atomically: rows it did not fill keep their stored line byte for byte, filled rows are re-serialised through the contract with every other field equal, and the new file must decode to the expected rows before it replaces the old one; it then re-renders `LEDGER.md`. A row whose diff is empty (a commit already contained in its base) is left as it is.

## Limits

A runner test with scripted inference under real Docker and a real ephemeral Temporal server proves the lifecycle and the records, not model accuracy. A live tier run is a small-n diagnostic on one shared model endpoint: compare latency only at equal concurrency. Scorecards, run directories and the shared store under `.runs/` are private evidence; reference scorecards are copied under `evals/baselines/candidates/` only by the orchestrator, and nothing is promoted.
