# Assessment and chain evaluation sets with durable chain mode

## Goal and scope

Two follow-ups that [SPEC-0030](SPEC-0030-evidence-assessment-agent.md) and [SPEC-0031](SPEC-0031-fixture-direct-composition.md) left open, and that [IDEA-0004](../ideas/IDEA-0004-end-to-end-agent-plan.md) lists before E2E-1:

1. **Scored evaluation sets.** A native Pydantic Evals dataset for the evidence assessment stage over frozen typed evidence, with development and held-out splits (SPEC-0023), so prompt and skill changes are judged on cases rather than smokes (PLAN-0029). A smaller chain dataset scores the whole E2E-0 composition over variants of the SPEC-0018 pair.
2. **Durable chain mode.** The same E2E-0 composition under one parent Temporal workflow with one child workflow per agent stage and an activity per frozen revision execution, reusing each stage's existing factory, contracts and routing (IDEA-0004 E2E-1, without OpenShell).

Excluded: OpenShell execution in durable mode (the kind cluster is reserved; the durable executor takes the same `Runners` the direct mode does, so the sandbox runner from PLAN-0034 plugs in unchanged), new agent prompts or skills, an LLM judge, report rendering, real repositories, the environment agent, and any change to the gates.

## Boundaries and design

**Assessment dataset** (`evals/evidence_assessment/`). `Case.inputs` is the stage input contract `AssessmentInput`; `expected_output`/`metadata` hold the oracle, never inputs. Cases are generated by a deterministic builder from typed evidence: native runs of the reviewed SPEC-0018 pair supply real JUnit and receipt text, typed transformations derive the negatives, `composition.evidence.evidence_items`/`run_evidence` produce exactly the items and gate evidence the chain produces, and witness items use the SPEC-0033 probe-record format. Classes come from IDEA-0004's assessment row: true pair; failed control; skipped and erroring security test; discovery error; unknown delivery; timeout; sandbox denial on either revision; contradictory repeats; unrelated baseline exception; missing baseline witness; witness safe behavior that differs from the plan; noncomparable candidate environment; patch digest mismatch; no candidate revision; injected instructions in test output. Each oracle carries the expected gate triple, which a configuration test checks against `assess` (so gate drift fails loudly), the honest proposal (the gate triple unless stated), the items a correct trajectory must read, and injection markers. Held-out cases have a content-hash manifest; a configuration test fails when one changes or a record cites one by name.

Scored dimensions, each reported separately: contract (typed output), gate admission (no over-claim), calibration (proposal equals the gate triple, so needless weakening also shows), witness grounding (a `reproduced`/`not_reproduced` finding cites a baseline witness item, a verified fix cites both revisions' witness items, matching the PR #34 output-function rule), trajectory (required items read before proposing), security (injection cases neither over-claim nor echo the injected text), efficiency (requests, tool calls, tokens, corrections, latency, native `MaxModelRequests`/`MaxToolCalls`), provider usage coverage, and consistency across repeats (per-case agreement of proposed triples). Scripted mode replays each oracle through a `FunctionModel` with real requests blocked; it proves plumbing and evaluator sensitivity, not interpretation quality.

**Chain dataset** (`evals/fixture_chain/`). `Case.inputs` names a revision mapping over the reviewed pair (vulnerable to fixed, reversed, both vulnerable, both fixed) or an identification abstention; the oracle holds the expected stop stage, gate triple and whether the assessment is admitted. The task runs the existing composition in direct or durable mode with the same scripted or live stage models as `evals/fixture_e2e`, whose runner is reused, not rewritten. Without a witness (main before SPEC-0033) every completed variant stops at `inconclusive`/`not_verified`, so the dataset's discrimination between variants arrives with witness capture; the oracle records which values depend on it.

**Durable chain** (`src/corsair/workflows/chain.py`). Routing stays in one place: the direct composition is split into a mode-independent `run_chain` over two injected ports, a stage invoker and a revision executor, plus an operation-id source and clock, and `run_direct` keeps its signature. In durable mode the parent workflow supplies a child-workflow invoker (one concrete workflow per stage, each registering exactly the agent its factory builds with native `TemporalDurability`, so model requests and tools are activities; the stage `timeout_seconds` becomes the child's execution timeout) and an activity executor (one activity per frozen revision run, `maximum_attempts=1`: a run with unknown delivery is recorded, never retried). Operation ids come from `workflow.uuid4()` and elapsed time from workflow time, so histories replay. The authoring stage's development runs need a runner on the worker: a `TemporalRunContext` subclass serializes the authoring dependencies' inputs and budget and resolves the runner on the worker from the operator's `Runners` by purpose, the native extension point, so the agent's tools and contracts are unchanged. Models are registered by key with each stage's durability; the request names keys only. Stage outputs, usage, messages and failures cross workflow boundaries as typed records.

## Acceptance and validation

Implementation: datasets round-trip through the native file format; builder regeneration is byte-identical; every oracle gate triple equals `assess`; held-out guard and record-citation guard; scripted runs pass every evaluator, and a scripted over-claiming or weakening model fails the matching evaluator; the task passes `inputs` only. Durable: direct and durable runs of the scripted chain give identical routing, gate verdicts and admissions on every chain case, under a native Temporal service; recorded histories replay; a revision activity failure is recorded once and not retried; an over-budget or timed-out stage closes attributably. Offline `make test-config` passes.

Live: one baseline run of the assessment dataset on the local provider (development split, three repeats, concurrency one), and the chain dataset with live identification, planning and assessment, both retained privately and summarized in PLAN-0037. A baseline is a measurement, not qualification.

## Decisions and open questions

Default chosen where the ask forked: the chain is durable with child workflows per stage rather than one workflow running four agents, because IDEA-0004 names that shape and it keeps each stage's activity identities and budgets separate. Expected rebase: PR #35 (witness capture) changes the execution block of the direct composition and the evidence items; PR #34 changes the assessment output function and prompt version. Open: whether the held-out split needs more cases once real-repository evidence exists; whether the assessment's rejected-proposal rate becomes a promotion metric (SPEC-0030). Plan: [PLAN-0037](../plans/PLAN-0037-assessment-evals-and-durable-chain.md).
