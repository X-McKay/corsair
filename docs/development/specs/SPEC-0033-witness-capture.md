# Execution-node witness capture

## Goal and scope

The [SPEC-0027](SPEC-0027-disposition-gates.md) gates admit `reproduced` only with a witness that the planned effect occurred, and `verified` only with a witness that the target was reached and rejected the input with the planned safe behavior. Until now nothing produced one, so every [SPEC-0031](SPEC-0031-fixture-direct-composition.md) verdict stopped at `inconclusive`/`not_verified` by design. This component makes the execution node capture a typed witness for each frozen revision run, independently of the test's assertions, JUnit and captured output, and maps it to the gate's `Witness` and test-phase `SandboxEvent`s.

In scope: Python component-scope tests run by the native pytest runner ([SPEC-0028](SPEC-0028-test-authoring-agent.md)) in the reviewed host workspace and the OpenShell test workspace ([SPEC-0032](SPEC-0032-openshell-test-workspace.md)); the file-open effect (path traversal and similar file reads). Excluded: other languages and runners, network, process and deserialization effects, application-path scope, durable mode, and any change to the gates, the agent contracts or the reviewed SPEC-0018 bytes.

## Boundaries and design

**Why not a kernel observer alone.** An unprivileged observer in another process can see that a file was opened (inotify; strace, fanotify and eBPF are unavailable in the pinned toolchain image and sandbox), but it cannot attribute the open to the application rather than the test's own fixture reads, and it cannot see a Python exception. It could therefore support `reproduced` but never `verified`, and it would need operator-planted sentinels that change the planner, author and reviewed test bytes. Out-of-process capture stays a later, layered cross-check (see open questions).

**Probe.** `nodes/witness_probe.py` is a repository-owned pytest plugin using only the standard library and native pytest hooks. It registers its own `sys.monitoring` tool (id 4) for `PY_START`, `PY_RETURN`, `PY_UNWIND` and `RAISE`, and a native audit hook (`sys.addaudithook`), before pytest imports any test module. Code objects match the target by `co_qualname` equal to the identified symbol and a resolved `co_filename` equal to the workspace root joined with the identified path; matches are cached by code-object identity, because equal code objects from another file or qualname compare equal. Only during each test's call phase (a `pytest_runtest_call` wrapper, so fixtures and teardown never count) it records per test: target entries, each exit (`None` for a return, the exception type for an unwind: a builtin by bare name, any other class as `module.qualname`, so a local lookalike never matches the planned builtin), every audit `open` whose calling stack contains the target and no importlib frame (module loading is never the effect), and every `OSError` raised with the target on the stack, once per exception object although `RAISE` fires in each frame it crosses (type and errno). Lists are capped at 32 with a `truncated` flag. At session finish it checks that its tool is still registered with unchanged events (`intact`) and writes one JSON record with `O_EXCL|O_NOFOLLOW` to an operator path; if anything already occupies that path, the run's exit status becomes pytest's internal error, so a planted or test-written record fails the execution instead of being read.

**Injection and read-back.** The target comes from the admitted `IssueIdentification.target` (`symbol`, `source.path`), never from plan prose or test code (`composition.evidence.witness_request`). `PytestRunner.run(..., witness=WitnessRequest)` needs `PytestRunnerConfig.witness_record_path` (distinct from the JUnit path and every patch path). The execution argv replaces the operator command's single `-m pytest` with `-c BOOTSTRAP PROBE_SOURCE CONFIG`: a fixed bootstrap executes the probe source passed as an argument and calls `pytest.main(args, plugins=[probe])`, so no file is added to the admitted workspace tree and no image changes. The config carries the workspace root, target, record path, tool id and a nonce `uuid5(operation, 'witness-nonce')`. Discovery and authoring development runs are unchanged. Only after a `completed` execution, one fixed command (`/bin/sh -c 'cat -- "$1"'`, operation `uuid5(operation, 'witness')`) reads the record through the same execution port; a non-zero exit, empty or oversized (64 KiB) output, an incomplete receipt or a storage failure makes the capture `unavailable`, and nothing is retried. `NativeTestRun.witness` holds a `WitnessCapture{status, request, nonce, probe_sha256, record, artifact, detail, receipt}`; the record bytes are stored as an artifact.

**Mapping** (`nodes/witness.witness_evidence`, pure host code). Refused (no witness, no sandbox events, a stated reason) when: no capture or unavailable; another request or probe digest; artifact digest not matching the bytes; the record fails strict validation; schema, nonce, probe digest or target differ; the tool was not registered or monitoring changed; the security test's call phase is absent or incomplete; entries and exits do not pair. Otherwise for the security test: `path_reached` is whether the target was entered; `effect` is `observed` when the target opened a file and no non-permission `OSError` occurred on its stack, `unknown` when such an error occurred, `absent` when it opened nothing; `safe_behavior` is the single exception type every target call unwound with, else `None`. Each `EACCES`/`EPERM` raised on the target's stack becomes `SandboxEvent{policy_denial, test, touches_witness_path: None}`, so the gate attributes the run to the sandbox; an empty tuple means none was observed on the witness path, which is the scope of that observation. The composition passes witness and events together to `run_evidence`, records a limitation per refused witness, and exposes only admitted records to the assessor as `witness` evidence items. An identified symbol or path the probe cannot address runs both revisions without a witness and records why, instead of stopping the chain.

**Authority and limits.** The probe is operator code, not workload code, and its record is a separate artifact from the test's pass/fail claim, which is what the gates require. It runs inside the test interpreter, so it is tamper-evident (own tool registration and events, operator nonce, exclusive record creation, nonce/probe/target binding on the host) but not tamper-proof: hostile test or repository code in the same process can still disable an audit hook through native code or forge a record before the probe writes it with knowledge of the nonce. Opens are attributed by the calling stack in the same thread; work the target hands to another thread or process is not attributed. An audit `open` fires before the system call; an open that then fails is visible only through the raised `OSError`. `observed` means the target opened some file during the security call, not that it opened the planned file: a target that legitimately reads a configuration or template file, or a test-supplied callback that opens one inside it, also yields `observed`. That is acceptable for single-purpose fixture targets and is the main reason a typed planned path is the next refinement. An abandoned generator target has no exit event and is refused as unpaired.

## Acceptance and validation

Offline (`tests/unit/test_witness.py`, `tests/unit/test_pytest_runner.py`, `tests/agents/test_fixture_composition.py`): the real probe in real pytest subprocesses attributes the target's open and not the test's own read of the same file; a rejection yields `absent` with its exception type; an uncalled target yields `path_reached: False`; a permission error becomes a sandbox event; a swallowed failed open leaves the effect unknown; changed monitoring, an occupied tool id, a record written by the test, another nonce, probe, target or artifact, malformed or incomplete records and unpaired exits are all refused; the runner injects the probe, reads once under its own operation id, never reads after a failed execution, refuses missing or conflicting record paths and reports unreadable records as unavailable; the probe argv stays well under the execution adapter's 16384-byte bound; and the composition over the reviewed pair now permits `completed`/`reproduced`/`verified`, while the same chain without witness capture stays `inconclusive` and rejects an over-claim.

Live (`make qualify-witness`, marker `witness`): the SPEC-0032 recipe on a fresh admitted kind node with the probe, two fresh sandboxes per variant; every record admitted with no sandbox event, vulnerable `(True, observed, None)`, fixed `(True, absent, ValueError)`; the gates over the four runs permit `completed`/`reproduced`/`verified` with no limitation; confirmed cleanup. This qualifies capture for the reviewed fixture only; model-authored tests, other targets and real repositories remain unqualified.

## Decisions and open questions

Default chosen where the design forked (put to the user as a decision card, work continued on the recommendation): an in-interpreter operator probe now, because it is the only mechanism that can support `verified` with existing tests and contracts; its tamper limit is recorded rather than hidden. Open: matching opens against a typed planned path (or outside the allowed root) instead of any non-import open; a layered out-of-process cross-check (inotify on an operator-planted sentinel, or OpenShell proxy events for network effects) as a separate record; typed planned effects (`open`, `connect`, `exec`) once a second effect kind is needed; witness capture for Java/Surefire; whether the probe should also bind the control test's target entry as evidence. The plan is [PLAN-0033](../plans/PLAN-0033-witness-capture.md).
