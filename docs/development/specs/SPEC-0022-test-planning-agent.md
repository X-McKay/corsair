# Read-only test planning agent

## Goal and scope

Implement the third planned agent of the [architecture](../../architecture.md) graph as an independently runnable PydanticAI stage, following the build order in [IDEA-0003](../ideas/IDEA-0003-remaining-agent-graph-inventory.md). Given an admitted issue identification, operator-supplied environment evidence and the saved source inventory, it produces the two-test specification the [investigation contract](../../investigation-contract.md) requires: one benign control and one security regression, each naming its fixtures, the real implementation call, required behavior, observable witness, discovery command and scope limits. It writes no test code, executes nothing and emits no finding or fix verdict.

Excluded: test authoring, the environment stage that will later produce the evidence contract, the parent investigation workflow, real-provider qualification and every real corpus case. The identification it consumes is still gated by ISSUE-0007 and SPEC-0024; this stage can be evaluated over frozen, reviewed identification fixtures independently.

## Boundaries and design

**Package.** `src/corsair/agents/test_planning/` mirrors the issue-analysis layout verified on main: `agent.py` (factory, `PROMPT_VERSION`, `CONFIG_VERSION`, trusted output function), `contracts.py`, `skills/__init__.py` with `skills/plan-two-tests/SKILL.md`, and no `tools/` package of its own. Evaluation lives in `evals/test_planning/` (`evaluate.py`, `fixtures/*.json`, `oracles.json`) and deterministic tests in `tests/agents/test_test_planning.py`.

**Shared code, now with a second consumer.** The planner needs the same confined saved-source inventory, `read_source` toolset and `SourceReference`/`SourceExcerpt`/`SourceRead` citation contracts as issue analysis, and the same `LocalModelConfig` provider seam. Those move from `agents/issue_analysis/` to `agents/source/` (contracts and toolset) and `agents/provider.py`, with the issue-analysis package re-exporting its public names so existing imports, tests and the durable fixture histories' tool identity (`issue_analysis_source`) are unchanged. This is the demonstrated second consumer the principles require; nothing else is shared.

**Inputs.** `TestPlanningInput` is an immutable Pydantic contract with no SDK objects: the authorized `scope`; an `IssueIdentification` from SPEC-0024 whose status must be `ready` (an abstention is refused at construction, not planned around); the saved `source_files` inventory, which may include existing test files, under the SPEC-0014 limits; and `EnvironmentEvidence`. That evidence is operator-supplied data today and the future environment stage's output later: language, runtime and framework identities, the native discovery command tokens, approved test paths, the discovered and executed baseline test identity, and the scratch location fixtures may use. Evaluator labels, variant names and the fixed revision never enter the input. The identification is supplied without its quotation; source evidence is re-derived from reads. Its preserved report describes a concern, not a proven effect, and remains untrusted task data including any embedded instructions. The planner must derive the conditional test hypothesis and necessary setup from that concern, the located implementation and environment evidence.

**Skill.** One mandatory operator-owned procedure, `plan-two-tests`, delivered eagerly through native `Capability` as SPEC-0019 established, recorded by SHA256. It covers: confirming the located implementation and identifying the sensitive operation by reading source before planning; reading the baseline test for conventions; choosing a benign input through the real path and an adversarial condition from the reported concern; making necessary resource/access conditions explicit in fixture setup; stating the required safe behavior precisely (a specific rejection or absence of effect, never an arbitrary exception); naming an observable witness and separating the application observation from a sandbox observation; keeping fixtures inside the scratch location; and returning `unsupported` with limitations when the hypothesis cannot be observed at the authorized scope with the supplied environment. It contains no language, framework or case-specific recipe; those facts arrive as environment evidence.

**Tools.** Only the shared `read_source` tool, with the existing zero tool-retry budget. No execution, write, shell, network or filesystem tool exists for this stage, so no execution backend is configured.

**Output.** `TestPlanDraft` (model-facing, line references) and `TestPlan` (final, exact quotations), following SPEC-0020, each a native Pydantic discriminated union on `status`. `ReadyTestPlan` carries `scope`, exactly two `TestSpecification`s named `control` and `security`, `discovery_command` tokens, `evidence_requirements`, `citations` and `limitations`; each specification states `test_id`, `test_path`, `fixture_setup`, `implementation_call`, `input`, `required_behavior`, `observable_witness` and `source_references`. `UnsupportedTestPlan` carries `scope`, `missing_capability` (the observation the supplied environment or authorized scope cannot support), `limitations` and optional `citations`, and no test specification at all, so an honest refusal never has to invent a setup, call or witness to pass validation. Pydantic refuses, on the ready branch, a third test, identical test ids, a test path outside the approved paths, a discovery command whose tokens differ from the evidence's command, and missing citations; on both branches it refuses unknown fields including any verdict. The trusted output function admits only the input scope and, for a ready plan, citations covered by successful `read_source` returns stamped with the current `run_id` and an `implementation_call` naming the identified target; it attaches quotations. An unsupported plan must still cite source read in this run when source was listed, so abstention is grounded rather than reflexive. These checks establish structure and provenance, not that a planned assertion measures the right property or that an abstention was warranted.

**Modes and budgets.** The factory takes an explicit `Model`, separate `retries={"tools": 0, "output": n}`, content-excluded native instrumentation and an optional injected `TemporalDurability`, so direct and durable modes reuse one factory as SPEC-0015 established. Callers inject `UsageLimits`; nothing in the prompt can change them. Durable registration gets its own later workflow; none is added here.

## Acceptance and validation

Deterministic checks with `TestModel`/`FunctionModel` and real-request blocking: accepted plan over the reviewed fixture; an unsupported plan accepted with no test specification and refused when it carries one; refusal of a non-ready identification, a third test, duplicate ids, unapproved test paths, altered discovery tokens, uncited or stale-run citations, scope expansion, verdict fields and an implementation call that does not name the identified target; skill and tool delivery on the actual native request; local span coverage.

Native Pydantic Evals over frozen development cases, two repeats, concurrency one: the SPEC-0018 pair supplies the first oracle, since `benchmarks/fixtures/path-traversal/test_documents.py` is the reviewed realization of a correct plan (allowed sentinel control, outside sentinel inside scratch, specific `ValueError`, open-event witness, exactly two tests). Negative cases: environment evidence without a discovered baseline test, an identification whose relevant implementation is absent from the inventory, an observation the environment cannot support (for example a witness needing a facility the evidence does not list), and instruction injection inside a saved test file. The first three expect the unsupported branch with a concrete `missing_capability` and no fabricated test details. Dimensions reported separately: oracle correctness, contract adherence, read-before-cite trajectory, tool correctness, robustness, security authority and estimated usage.

Semantic adequacy (no mocked sink, no constant assertion, witness actually observes the effect) cannot be proven by these checks; independent review of actual outputs remains mandatory before any live qualification, as ISSUE-0007 showed for the analyst. Live provider repeats, durable composition and connection to the graph are separate gates and are not claimed by this spec.

## Decisions and open questions

The planner precedes the environment agent because it is read-only and its inputs can be frozen now, while environment execution waits on ISSUE-0006 and a setup-recipe contract. `EnvironmentEvidence` is deliberately minimal and operator-authored; the environment stage will have to produce exactly this contract or supersede it explicitly. Whether a per-framework convention reference (pytest, JUnit 5) belongs in the environment evidence as admitted data or in a second skill is open; the default is data, to keep the skill general across languages. Whether the planner should see the existing baseline test content or only its identity is resolved as: content, through the inventory, because conventions matter and the inventory is already bounded. A plan and a later implementation record will follow if this spec is accepted.

The user accepted narrowing the analyst in SPEC-0024. This draft now consumes the small identification handoff; the legacy IssueAnalysis hypothesis output is not silently converted. Planner implementation and admission remain separate work, with actual test validity and execution evidence required before dispositions.

Accepted with IDEA-0004 and implemented offline under [PLAN-0025](../plans/PLAN-0025-test-planning-agent.md). Implementation refinements: `EnvironmentEvidence` carries `observation_facilities` and `BaselineTest{test_id, path}` (whose file must be in the inventory); the draft union arrives as one `plan` argument of the native output function; approved paths and discovery tokens are enforced by the contract validator under native validation context; `ReadyTestPlan` adds `security_expectation{failure_type, safe_behavior}` as typed identifiers for the SPEC-0027 gates (assertion lines belong to the authoring patch); the stage uses the windowed `read_source` (tool-computed end); evaluation uses a native `cases.yaml` with metadata oracles rather than `fixtures/*.json` and `oracles.json`. Live provider qualification remains open.
