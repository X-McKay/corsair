# Deterministic disposition gates

## Goal and scope

Build the first `core/` module named in [IDEA-0004](../ideas/IDEA-0004-end-to-end-agent-plan.md): given frozen per-revision execution evidence, compute the strongest `execution`/`finding`/`fix` triple the [investigation contract](../../investigation-contract.md) permits, and admit or reject a proposed triple against it. The future evidence assessment agent proposes; these gates decide, and they are useful without the agent because the permitted triple can go straight to the report.

Excluded: the assessment agent, its `read_evidence` tool and citation resolution; the native runner adapter that will produce these inputs from JUnit XML, witnesses, receipts and sandbox logs; the report renderer; any live run. `refuted_in_scope` is never admitted here, because it needs affirmative evidence that pass/fail outcomes and witnesses cannot carry.

## Boundaries and design

`src/corsair/core/disposition.py` is pure, vendor-free and deterministic: frozen `extra="forbid"`, strict Pydantic contracts and two functions, `assess(AssessmentEvidence) -> GateResult` and `admit(Disposition, GateResult) -> Admission`. It imports nothing from adapters, ports or agents.

**Inputs.** `AssessmentEvidence{plan, baseline: runs (at least one), candidate: runs (optional)}`. Revisions are `baseline` and `candidate`, never vulnerable/fixed. `ObservationPlan` holds typed expectations: control and security test ids, the frozen patch digest, the expected security failure (exception type, test path, test function and the planned assertion lines in the frozen patch) and the expected safe-behavior token (for SPEC-0018, `ValueError`). Each `RunEvidence` is one fresh execution: delivery and completion, an execution failure layer if any, observed patch digest, discovered test ids, per-test outcome (`passed`, `failed`, `skipped`, `error`) with a bounded `ClassifiedFailure` for failures, a `Witness` captured outside the pass/fail claim (artifact digest, whether the sensitive path was reached, whether the effect was observed, the observed safe-behavior token), an `EnvironmentIdentity` (image, recipe, dependency inventory, policy revision, limits) and sandbox events (policy denial or resource limit, phase, whether it touches the witness path).

**Per-run classification**, in order. Unknown delivery or completion: execution `unknown`. A recorded execution failure: `blocked` for policy or sandbox layers, `unknown` for an unknown layer, otherwise `failed`. Patch digest mismatch, discovery other than exactly the two planned ids, a skip or a JUnit error (setup, fixture, teardown): `failed`. A test-phase sandbox event that touches, or may touch, the witness path: `blocked` and sandbox-attributed. Otherwise the run completed and is classified: failed control is `control_failed`; a security failure is `reproduces` only when every classification field is known, it matches the planned exception, path, function and an assertion line, and the witness shows the effect observed; a security pass is `safe` only when the witness shows the path reached, the effect absent and the planned safe behavior. Anything else is `unusable` with a coded limitation (`unclassified_failure`, `unplanned_failure`, `witness_missing`, `witness_unsupported`).

**Disposition.** Finding depends only on the baseline: any `control_failed` run or a mix of `reproduces` and `safe` runs gives `inconclusive`; otherwise at least one `reproduces` gives `reproduced` (unusable repeats recorded as `incomplete_repeats`, not erasing the reproduction); all runs `safe` gives `not_reproduced`; anything else `inconclusive`. Fix is `not_applicable` without candidate runs. Otherwise it is `verified` only when every baseline run reproduces, every candidate run is `safe`, and every run on both revisions has the identical environment identity; any other case gives `not_verified` with the reason recorded. Candidate-only problems never weaken a valid baseline finding. Execution is the worst run state, ordered `unknown`, `blocked`, `failed`, `completed`; `unsupported` comes from earlier stages, never from run evidence.

**Admission.** A proposal is admitted when execution equals the observed value; finding equals the permitted value or is the weaker `inconclusive`, and is never `refuted_in_scope`; fix equals the permitted value or is the weaker `not_verified`, `not_applicable` must match exactly, and `verified` requires a proposed `reproduced` finding. A rejected proposal returns every reason and the gate's permitted triple.

Bespoke code is necessary because no SDK in the stack encodes the investigation contract's verdict rules; the module is about 300 lines and has no runtime dependency beyond Pydantic.

## Acceptance and validation

Table-driven unit tests in `tests/unit/test_disposition.py` over SPEC-0018-shaped synthetic evidence: the true reproduction and verified fix; the same pass/fail outcomes with an unrelated baseline exception, a non-planned assertion line, an unclassifiable failure, a missing or contrary baseline witness (expect `inconclusive`/`not_verified`); a valid baseline with a sandbox-denied candidate rejection, an unknown-scope test-phase event or a noncomparable candidate environment (expect `reproduced`/`not_verified` and the limitation); contradictory baseline and candidate repeats; failed controls on either revision; skip, fixture error, compile failure, extra discovered test, patch mismatch, unknown delivery, timeout and policy-blocked execution; incomplete repeats with reproduced or safe baselines; candidate passes for the wrong reason, without reaching the path or without a witness; admission of equal, weaker and stronger proposals; deterministic repeat; and contract refusal of empty baselines, duplicate planned ids, failure details on non-failed tests, extra fields and malformed digests.

Implementation checks are not qualification. The gates' inputs are typed claims; their correctness depends on the future runner adapter classifying actual JUnit and capturing witnesses faithfully, which is separate work.

## Decisions and open questions

Defaults chosen where the plan forked: a failed control in any execution-valid run blocks a conclusive finding on that revision rather than being treated as an incomplete repeat; `not_reproduced` requires every baseline run to be safe, while `reproduced` survives incomplete repeats; fix verification requires every baseline and candidate run to be valid and comparable; a test-phase sandbox event with unknown reach counts as touching the witness path. Typed expectations, settled with the planner thread on 2026-10-12 (its draft PR #26): `ReadyTestPlan.security_expectation{failure_type, safe_behavior}` supplies `expected_failure.exception_type` and `expected_safe_behavior`; the security specification's `test_path` and `test_id` supply the path and function; the test authoring stage's frozen `TestPatch` supplies `assertion_lines`. A small builder from those two contracts to `ObservationPlan` lands once both are on main; until then `ObservationPlan` is constructed by trusted test code. Checked against draft PR #28 on 2026-10-12: `TestPatch.security_assertion_lines`, `patch_sha256` and `security_test_id` map directly, and the runner's `FailureDetail{kind, type, path, function, line}` maps to `ClassifiedFailure` with `kind="error"` becoming an `error` outcome. The assertion lines are model-declared and only checked to be assertions in the security function, so they are reviewer-checked input, not ground truth: a setup assertion declared as a security line would let the wrong failure count as planned. By design (SPEC-0028), the runner produces no `Witness`: everything it reads is produced inside the test process, so a witness needs its own operator-owned capture beside the run (sandbox or policy telemetry, or an observer the workload cannot write to), owned by the execution node. Until that exists, `RunEvidence.witness` is `None`, and the expected, correct gate result is `inconclusive`/`not_verified` (or `not_applicable`) with `witness_missing`; this is not a defect. Test ids and failure paths are workspace-root-relative and SPEC-0028 requires the workspace root to be the repository root, so they stay repository-relative; the retained SPEC-0018 runs predate that rule, record ids relative to a fixture copy (`::test_benign_control`, `test_documents.py:64`), and match only after an explicit rebase. The plan is [PLAN-0026](../plans/PLAN-0026-disposition-gates.md).
