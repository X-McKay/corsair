# Environment agent

## Goal and scope

[IDEA-0004](../ideas/IDEA-0004-end-to-end-agent-plan.md) (accepted) needs an environment stage for the first real case: a repeatable setup for one repository commit that installs dependencies, builds, discovers tests and runs one existing test, producing the environment evidence the planner ([SPEC-0022](SPEC-0022-test-planning-agent.md)) consumes. This spec fixes the agent's isolated contract, skill and tools so they can be built and tested deterministically now. It also records how the offline parts of [SPEC-0025](SPEC-0025-sandbox-source-fetch.md) and [SPEC-0026](SPEC-0026-sandbox-dependency-fetch.md) are implemented as deterministic nodes.

Excluded: any live provider, OpenShell or Temporal run; connecting the stage to a workflow; the setup-replay node; and any relaxation of the no-workload-credential rule. Live use stays blocked until SPEC-0025 and SPEC-0026 qualify (the storage quota precondition was replaced on 2026-10-13 by SPEC-0025's pre-flight workspace budget, quota recorded unqualified), and, for private repositories, confirmation of the OpenShell 0.1.3 credential placeholder behavior.

## Boundaries and design

**Input.** `EnvironmentInput`: the exact commit, whether the source is private, a bounded `source_files` inventory restricted to manifests, CI workflows and setup documentation (at most 32 files, 128 KiB), the admitted toolchain image catalog (id, digest-pinned image, language, runtime, tools), and the read-only policy profile identity. No labels, oracles or evaluator data. Operator-owned dependencies carry the execution port, the preparation sandbox handle and its toolchain, the scratch location and the command budget; nothing in the prompt can change them.

**Skill.** One mandatory operator-owned `prepare-environment` procedure, delivered eagerly through the native `Capability` and recorded by SHA256 (as in SPEC-0019): prefer the repository's native build tool and CI steps; cite the lines each step follows; never edit source, tests, policies, credentials or pins; never pipe downloads into a shell or probe outside the policy; report an unsupported toolchain rather than installing another; distinguish registry, TLS, dependency, toolchain, build, discovery and sandbox failures from native output; stop after an unknown delivery.

**Tools.** A stage-owned toolset: `read_source(path, start_line)` (80-line windows over the saved inventory, same shape as identification), `list_toolchains()`, `run_setup_command(command)` and `read_output(run_id, stream, offset)`. `run_setup_command` dispatches exactly once through the vendor-free `SandboxExecution` port (SPEC-0010) with a fresh operation id, records a trusted `CommandRecord` (command, operation, delivery, completion, exit, failure layer, output digests, elapsed time) and retains the bounded output in a per-run ledger. Commands never retry. After an unknown delivery or completion, or any port-level execution error (for example a result-journal failure or unconfirmed worker cleanup, which can accompany exit 0), no further command is dispatched, and such a run never counts as successful. The operator budget (default 12 commands) is enforced by the tool. The sandbox policy and limits, not the tool, are the security boundary: tokens are argument vectors and are not interpreted on the host.

**Output.** A native discriminated union on `status`, with a model-facing draft (line references) and a final form (exact quotations, SPEC-0020):

- `ReadyEnvironment`: toolchain id, `recipe` steps (phase `dependency` or `build`, command tokens, cited source), `build_command`, `discovery_command`, `framework`, `baseline_test_id`, `baseline_test_path`, `baseline_test_command`, `approved_test_paths`; trusted code adds `toolchain_image`, `language` and `runtime` from the catalog, `baseline_outcome: passed`, `scratch_location` and all `receipts`.
- `BlockedEnvironment`: `layer` (dependency, registry, tls, toolchain_version, build, discovery, sandbox, unknown), quoted `evidence`, cited `run_ids` and optional citations, plus receipts.
- `UnsupportedEnvironment`: the unmet `requirement` with at least one citation, plus receipts.

The trusted output function admits ready only when, in the current run: every citation is covered by a successful `read_source`; no command had unknown delivery; the toolchain is the preparation sandbox's; the recipe commands, build, discovery and baseline test commands all succeeded as an ordered subsequence of observed commands; the discovery command's retained output contains the baseline test id; and an operator-owned framework entry (`pytest`, or `junit5` under Maven Surefire) admits the baseline: the test id's file component equals `baseline_test_path` exactly (repository-relative for pytest, the class path under a source root for Java), the baseline command's effective selector is exactly that id (one pytest node-id argument with no `-k`, `-m`, deselect, ignore or last-failed options; exactly one Surefire `-Dtest=` selector naming that method, with no other Surefire selector property), and its output reports exactly one passed test with nothing skipped, xfailed, deselected or errored (warning counts are allowed). Exit 0 alone never yields `passed`. That summary is still workload-printed; the native runner adapter in IDEA-0004 replaces it with JUnit XML. Any other framework cannot be admitted ready. Blocked must cite commands from this run, at least one cited run must have failed, and the evidence must be an exact excerpt of a failed cited run's retained output or execution error; a blocked result without cited runs is admitted only for layer `sandbox` or `unknown` after a halt or an exhausted budget. The excerpt grounds the claim; choosing the layer from it remains the model's judgement. Unsupported must be grounded in read source.

**Dependency closure.** IDEA-0004 lists a closure in the ready output. The model never authors digests: the realized on-disk inventory comes from the operator inventory receipt (SPEC-0026), parsed by the deterministic node below and attached by the setup-replay node, which compares a fresh replay against it. The planner's `EnvironmentEvidence` (SPEC-0022, implemented concurrently on the test-planning branch) holds language, runtime, framework, discovery command, approved test paths, baseline test id and path, scratch location and observation facilities. `ReadyEnvironment` carries every field except observation facilities, which describe the operator's sandbox rather than the repository and stay operator data; the mapping is a composition step once both are merged. The ready check also requires the baseline test path to be the file named in the discovered test id.

**Deterministic nodes.** `corsair.nodes.source_fetch` implements the SPEC-0025 offline contract: an operator-owned fetch recipe whose shell script is a fixed constant with data passed as positional arguments; refusal of non-HTTPS, credentialed or non-allowlisted URLs and non-SHA commits; materialization from raw blobs so no `.gitattributes` transformation applies; a strict receipt parser; and host admission against the `SourceSnapshot` by commit, tree and file-by-file raw-byte SHA256, mode and size, refusing missing, extra, modified, non-regular and extra-directory entries, receipts containing a secret, and unknown or failed delivery. A refusal always means discard the sandbox. `corsair.nodes.phase_policy` builds the three ordered policy revisions (repository host for the git transport only; GET-only per-ecosystem registries refused for private source; no network). `corsair.nodes.dependency_inventory` parses and compares realized inventories with explicit generated-file lists. Applying a revision with `policy set --wait` and observing the denial event remain adapter work for live qualification.

**Modes.** One factory with an explicit `Model`, `retries={"tools": 0, "output": n}` and content-excluded native instrumentation. Durable registration is deferred: in Temporal the command tool would be an activity whose unknown outcome must not be replayed, which needs its own qualification.

## Acceptance and validation

Deterministic, with `FunctionModel`, real-request blocking and a scripted execution port: ready admitted with trusted fields; refusal of a recipe step that never ran, a failed baseline, discovery output missing the id, wrong order, uncited or unread citations, a non-prepared toolchain; unknown delivery halts dispatch and forbids ready; budget enforced by the tool; blocked refused with invented or only-successful runs; unsupported grounded and refused without a read; contract refusal of path escapes, duplicate paths, empty or NUL tokens and verdict fields. Node tests cover the SPEC-0025/0026 offline acceptance lists, plus one local test that materializes a real repository with CRLF and `ident` attributes byte-identically through the fixed script.

Not covered and not claimed: any live provider behavior, evaluation dimensions beyond these deterministic contract and trajectory checks, OpenShell execution, policy loading, credential placeholder behavior, storage limits, replay drift or durable mode. The evaluation plan in IDEA-0004 (correctness by fresh replay, robustness against missing dependency, registry/TLS denial and wrong JDK, injection in README/CI) needs the qualified runtime.

## Decisions and open questions

Defaults chosen: command tokens rather than a shell string, with the sandbox as the boundary; one preparation sandbox per run, with a toolchain mismatch reported rather than worked around; closure digests attached by deterministic nodes, not the model; read failures and budget refusals are returned to the model as failed tool results (`ToolFailed`) bounded by run usage limits, so it can report blocked. The materialized checkout's workdir is the repository root and is the command working directory, so discovered test ids stay repository-relative as SPEC-0028 requires; pytest discovery should name the root explicitly (for example `-c /dev/null --rootdir .`), and the ready check refuses a baseline id whose file part is not exactly `baseline_test_path`. Approved test paths may not equal a saved inventory path. Typed execution witnesses (path reached, effect observed or absent) captured outside the workload are not provided here: the only qualified sandbox telemetry is OpenShell's native network policy decision and denial events (SPEC-0006), which can attest egress attempts but not file access or in-process effects, so a general witness is separate future work owned by the execution node. Open: whether setup should run in a separate sandbox per phase or one sandbox moving through revisions (SPEC-0026 assumes one); the per-ecosystem inventory scripts; and the Temporal activity design. Implementation is tracked in [PLAN-0028](../plans/PLAN-0028-environment-agent-and-source-fetch.md).
