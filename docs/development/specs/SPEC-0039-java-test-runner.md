# Java test identity, Surefire reports and Maven runner

## Goal and scope

Close the offline half of gap G6 in IDEA-0005 (draft PR #39) for Java: the runner, report parser and test-id contracts were pytest-only, so no Vul4J case, JSPWiki included, could reach the SPEC-0028 runner. This spec adds a typed JUnit test id, a Surefire XML parser feeding the same `TestCaseResult`, `FailureDetail` and SPEC-0017 `AdmittedTestClaims` shapes, and a Maven runner with the same `TestRunner.run` contract as the pytest runner. It records what a Java witness needs; it does not build one.

Excluded: running a Java case in OpenShell (a later step on the kind cluster), the Java test authoring agent's static checks (G8), dependency closures and toolchain images for real cases (G4, G5), source acquisition (G2c), and any change to the gates or agents.

## Boundaries and design

**Test id.** `JavaTestId` in `ports/test_runner.py` is `[module/]package.Class#method`. The optional module is the Maven reactor directory relative to the repository root, so the id names one method in a multi-module build; with no module it is exactly the environment agent's `junit5` form (`agents/environment/frameworks.py`). Only top-level classes and ASCII identifiers are admitted: nested `$` classes, parametrized or display names, traversal, empty or option-like module segments and ids over the shared 128-character bound are refused. `source_path()` gives Maven's conventional file, `<module>/src/test/java/<package>/<Class>.java`, which must be a patch file. The SPEC-0017 claim schema and the SPEC-0027 gate `TestId` now admit `#`, so a Java run reaches the gates as `RunEvidence`; nothing else in `test-observations-v1` or the gates changes.

**Reports.** `reports/surefire.py` reads one `TEST-<class>.xml`. It reuses the JUnit parser's admission (byte bound, UTF-8, refusal of every markup declaration before expat, stdlib parse), now shared as `admit_xml`. It requires the root `testsuite` named after the ids' class, exactly one testcase per expected id keyed by Surefire's (classname, name), and refuses unexpected, duplicate or ambiguous testcases and any `rerun*` or `flaky*` element, because Surefire reruns would break the one-execution contract. Failure classification takes the exception type from Surefire's `type` attribute and the location from the topmost `at package.Class.method(File.java:N)` frame whose file maps to a patch file through the test source root; a `lambda$method$N` frame belongs to `method`. Captured output is the testcase's `system-out`, bounded as for pytest. Real reports from Surefire 2.22.0 (trimmed traces) and 3.6.0 (full traces) both parse.

**Discovery.** Superseded by [SPEC-0041](SPEC-0041-version-independent-junit-discovery.md), which lists tests with a pinned JUnit console launcher for any JUnit 4 or 5 version; the dry-run design below is kept as history. pytest has `--collect-only`; Surefire has no listing mode. The JUnit Platform's own dry run (`junit.platform.execution.dryRun.enabled`, Platform 1.13 and later) makes Surefire report each selected test as skipped with the message `JUnit Platform dry-run mode is enabled`, without running bodies. Discovery passes only when the dry-run report names exactly the two ids and every testcase carries that skip; any other outcome means the platform ignored the property and ran the bodies, so discovery is a `collection_error` and nothing executes in that workspace. Measured: JUnit 5.4.0 under Surefire 2.22.0 (JSPWiki's upstream POM) ignores the property and runs the bodies; JUnit 5.14.4 under Surefire 2.22.0 runs zero tests and exits 0; JUnit 5.14.4 under Surefire 3.6.0 honours it. The operator must therefore admit, per case, a dependency closure whose platform supports the dry run. Exact discovery without the property would need a fixed operator `Launcher.discover` helper in the image, which is not built.

**Runner.** `adapters/maven_runner.py` shares orchestration with the pytest runner through `adapters/native_runner.py`: one fresh workspace, release always runs, receipt completeness is checked and nothing is retried. The operator-owned `MavenRunnerConfig` holds the Maven argv (binary, `-B -o`, local repository, `-f <root>/pom.xml`, goal), the workspace root, the reports directory and test source root (Maven defaults), and bounds. Both stages run a fixed `/bin/sh` wrapper that removes the class report, runs Maven with its console on stderr, then prints exactly the report on stdout and exits with Maven's status; the report path and every argument are positional. The runner appends only the selection: for a module, `-pl <module> -am -Dsurefire.failIfNoSpecifiedTests=false` (reactor dependencies build but select nothing), then `-Dtest=<class>#<m1>+<m2>`; discovery also appends the dry-run property. Control and security must be methods of one class, so exactly one report is admitted. Execution outcomes: no report is an execution failure (Maven failed before Surefire reported), an exit other than 0 or 1 is an execution failure, an exit that disagrees with the reported outcomes is an invalid report, and otherwise claims are admitted bound to the stored report bytes. Skips are completed claims that the gates reject, as for pytest.

**Witness.** A `WitnessRequest` returns an `unavailable` capture and runs nothing, so SPEC-0027 gates see an absent witness and cannot conclude reproduced or verified. The SPEC-0033 probe cannot apply: it relies on CPython's `sys.monitoring` and audit hooks inside the pytest process. A Java witness needs an operator-owned observer inside the Surefire fork, delivered through an injection point the project cannot override (the `JDK_JAVA_OPTIONS` environment variable is read by every JDK 9+ `java` launcher, Maven's own JVM included, so the observer must scope itself to the fork; Surefire's `argLine` user property is ignored when a POM sets `argLine`), writing a nonce-bound record outside the report, read back by a separate fixed command. Candidates, native first: JDK Flight Recorder's `jdk.MethodTrace` (JDK 25, JEP 520) traces named method entry with no agent jar, and `jdk.FileRead`/`jdk.FileWrite` at threshold 0 record file paths on I/O but not opens; neither records arguments. A `java.lang.instrument` agent (`-javaagent`) can record target reach, file opens and call arguments, at the cost of a hash-pinned jar in the image and bespoke code. JSPWiki's effect is a dispatcher choice, not a file open, so it also needs argument capture (G7). Like the pytest probe, either option is tamper-evident at best because test code shares the JVM.

## Acceptance and validation

Offline: id parsing and refusals; the parser over nine real reports (`tests/unit/surefire/`, provenance in its README) and synthetic refusals for reruns, flaky elements, foreign classes, duplicates, ambiguity, declarations and malformed bytes; runner orchestration over fake ports replaying those reports, including discovery that ran bodies, missing reports, exit/outcome conflicts, execution errors without retry, witness requests and refused ids. Local host evidence (not sandbox, not qualification), recorded in PLAN-0043: the Maven runner driven through a local subprocess executor on the sample project, a two-module sample and JSPWiki at both commits.

Live qualification remains: the runner inside the SPEC-0032 workspace with a Java toolchain image carrying the admitted offline closure, on a fresh node.

## Decisions and open questions

Defaults chosen where the work forked: both tests in one class (one report; JSPWiki's draft already has this shape); discovery only by the platform dry run, refused otherwise; Maven console on stderr for diagnosis while stdout stays exactly the report; the JUnit-format pytest parser and the Surefire parser stay separate modules with one shared admission helper. Open: whether to admit `-Djunit.version=5.14.4 -Dplugin.surefire.version=3.6.0` for JSPWiki (test framework only, matching the qualified Java toolchain image; measured to give the hypothesised outcomes on the host) or build the `Launcher.discover` helper instead; Java 8 era builds on the JDK 17 image versus a JDK 8 or 11 image; Surefire report output above 256 KiB; nested classes and parametrized tests. The plan is [PLAN-0043](../plans/PLAN-0043-java-test-runner.md).
