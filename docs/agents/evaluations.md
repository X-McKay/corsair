# Agent evaluations

Agent evaluation has three distinct levels. Keep their evidence separate: a deterministic native-ADK test, an isolated live-model fixture evaluation, and a composed Docker/Temporal investigation answer different questions.

| Level | What runs | What it establishes | What it does not establish |
| --- | --- | --- | --- |
| Native test double | Tests use `ScriptedLlm`, a deterministic implementation of ADK's `BaseLlm`, with the real ADK runner/factories. | Factory wiring, schema/tool behavior, callback budgets, and SDK fallback regressions. | Provider behavior, target execution, or model accuracy. |
| Isolated agent evaluation | The installed `corsair.evaluation.agents` module calls the production factory and native runner against a frozen input with an explicitly configured live model. | A role's bounded output against its frozen diagnostic oracle. | Docker execution, Temporal durability, hostile-target resistance, or whole-system accuracy. |
| Composed evaluation | A worker, ordinary Temporal workflow, trusted Docker observer, immutable artifacts, policy, and external scorer process a frozen dataset. | The specified end-to-end cohort, including evidence validity and operational failures. | Population-level accuracy, production readiness, or universal target integrity. |

## Run isolated checks

Run these repository-root commands only with a deliberately selected settings file and the required provider configuration in the worker environment:

```bash
just -- eval-agent producer evals/datasets/producer-dev.json \
  --settings /path/to/settings.json --repeats 3
just -- eval-agent auditor evals/datasets/auditor-dev.json \
  --settings /path/to/settings.json --repeats 3
```

Validate the frozen manifests first; it takes well under a second and needs no provider, Docker or Temporal:

```bash
uv run --locked corsair dataset validate evals/datasets/producer-dev.json \
  evals/datasets/auditor-dev.json evals/datasets/dev.json
```

It verifies each entry's digests, input contract, source snapshot digest, the pre-model target-binding gate and the oracle's internal consistency, and prints the dataset digest and cohort membership to record with the run (see the [CLI reference](../reference/cli.md#dataset-validate-dataset)). A failure there would otherwise surface only on the rig.

`just eval-agent` invokes the installed module. The producer invocation admits an immutable local snapshot for source reads but does not run the target or any probe code on the host. The auditor invocation has no tools. Raw reports belong under ignored `.runs/`; retain sanitized baselines and experiment notes under [`evals/baselines/`](../../evals/baselines/) and [`evals/experiments/`](../../evals/experiments/).

Each frozen fixture input and oracle is read and digest-verified before use. The evaluator keeps its oracle local: it passes only the role input to the factory and compares the returned typed output outside the agent boundary. The producer diagnostic checks the exact canonical control payload and an allowed candidate payload; it is not semantic-equivalence or vulnerability-accuracy scoring. The auditor diagnostic checks its decision on the supplied source/submission packet without an observation or expected label. The auditor's rubric names its rules `R1` mechanism, `R2` differential, `R3` production logic and `R4` disclosure, not echo; each auditor row records the returned `audit_decision` and the decisive `audit_rule` (`ALL` for an acceptance) so a rejection is attributable. The rule is model output. When an oracle holds only a `decision` (the dev and expanded cohorts), the rule is reported but not scored. When the oracle also names a `rule`, a row passes only when both match, and the right decision under the wrong rule is the separate match kind `rule_mismatch`.

A provider policy block, provider failure, malformed output, or other operational error remains an operational failure in the report. No frozen label turns into a pass after a policy block. For full investigations, the external scorer holds the oracle outside agents, tools, and workflows; it scores terminal results only after trusted evidence validation and policy processing, retaining invalid positive evidence, forbidden labels, inconclusive outcomes, and operational failures in the record.

## Reading results

Isolated diagnostics compare payload values and audit decisions against frozen oracles; they are not population accuracy, a false-positive rate, hostile-target attestation, or automated baseline promotion. A composed live batch is scored externally on the six labels and retains invalid positive evidence, forbidden labels, inconclusive outcomes, and operational failures. Neither kind of result upgrades the other.

Each composed-batch row also carries a `gate_ledger`: one entry per recorded round (`session`, `round`, `stage`, `gate`, `reason`) naming what stopped it, followed by any case-level `policy` stop such as `budget_exhausted`, `negative_threshold_unmet`, `fix_not_blocked` or `execution_error`. Stages are `producer` (adapter gates such as `producer_invalid:llm_budget` or `provider_permanent`, and `producer_abstained`), `evidence` (the evidence feedback gate, `probe_invalid`), `audit` (`audit_reject`, `audit_invalid:*`, `audit_insufficient_context`, when an otherwise decisive pair was not accepted) and `kernel` (`coverage`, `no_differential`, `target_unbound`, `clean_negative`, `demonstrated`). The [ledger](../../src/corsair/evaluation/ledger.py) is derived by the external scorer from the recorded result and each round's own validated receipts; a round whose receipts do not validate is `evidence_unverified`. It describes the kernel's decision and never makes one. The report summary adds `gate_ledger` (counts of every entry) and `failure_stops` (counts of each failed row's final entry), and `corsair report` renders both as tables, so the dominant loss is read from the report rather than reconstructed by hand.

Each isolated agent row carries the same `gate_ledger` key with one entry (`session` and `round` unset, since the row is one episode). Its stage is `producer` or `audit` when the episode returned no valid output: the adapter's own gate with the same fixed qualifiers (`producer_invalid:llm_budget`, `producer_invalid:tool_budget`, `audit_invalid:malformed`, `audit_invalid:no_output`), an operational provider gate such as `provider_max_tokens` or `provider_permanent`, `producer_abstained` for an explicit abstention, or `audit_missing`. A valid output is compared at stage `oracle`: `exact_match`, `control_mismatch`, `candidate_exact_mismatch` or, for an auditor whose oracle names a rule, `rule_mismatch`. An auditor mismatch adds its own decision and, when it is one of the fixed rubric ids, the cited rule (`candidate_exact_mismatch:reject:R1`, `rule_mismatch:reject:R1`), never the oracle's expected rule. The entry is derived from the row's recorded `match_kind`, `feedback`, `audit_decision` and `audit_rule`; its reason is fixed evaluator text or adapter feedback and never contains oracle payloads or model-written review text. Agent summaries count `gate_ledger` and `failure_stops` exactly as composed ones, and `corsair report` shows each row's final gate in a `Stop` column. It never changes the exact-match pass rule.

The expanded datasets (`producer-expanded.json`, `auditor-expanded.json`) add AI-authored candidate cases pending human review; they are not held-out human labels.

`auditor-rubric.json` is the rubric cohort: one frozen packet per rubric outcome, with an oracle that names both the decision and the decisive rule, so each rule can fail on its own. `audit05` has a false mechanism (`REJECT`/`R1`). `audit06` has payloads that resolve to the same public file (`R2`). `audit07` substitutes a stub reader for the production function (`R3`). `audit08` presents an echo of the submitted string as disclosure (`R4`). `audit09` puts the containment logic in an imported helper the excerpt does not show (`INSUFFICIENT_CONTEXT`/`R1`, the first link that cannot be established). `audit10` (an unnormalised prefix check) and `audit11` (an absolute path that replaces the root in `os.path.join`) are two coherent claims expected to be accepted (`ACCEPT`/`ALL`). Run it as `just live-agent auditor evals/datasets/auditor-rubric.json` or with `eval-agent`. The seven cases are AI-authored candidates pending human review, like the expanded cohort: their labels are not human labels, and a result on them is a diagnostic, not a baseline. A candidate exact-string mismatch is a retained failure, not a reason to widen the oracle: alternate payloads require separately admitted trusted native replay before being called equivalent.

## Comparing two runs

Compare two saved reports on the same frozen dataset with `corsair compare BASELINE.json CANDIDATE.json` (see the [CLI reference](../reference/cli.md#compare-baselinejson-candidatejson)). It joins attempts by case and repeat, flags pass/fail flips, label changes and new forbidden labels, and reports usage deltas; it exits `1` on a regression. For both report kinds it also compares the ledgers: a `gates moved` line (for example `exact_match -2, producer_invalid:llm_budget +2`), a per-gate table of baseline count, candidate count and delta for every stop and for failed rows' final stops (`gate_delta` in JSON), and each changed attempt's final stop before and after. Isolated reports saved before rows carried a ledger derive it from their recorded fields, so an older baseline still compares per gate. Gate movement explains a regression; it never decides one. It refuses reports whose dataset digests differ or are undeclared unless `--allow-dataset-mismatch` is passed, and then marks the result as a mismatch. Report the dataset digest, the cohort of each side and any configuration digest change with the comparison. A comparison of two isolated diagnostics remains a role-level diagnostic, and a candidate with no regression on one frozen cohort is not a promoted baseline.

To record a report or comparison under `evals/baselines/candidates/`, in a pull request or in a plan, write it with `corsair --format markdown report REPORT.json` or `corsair --format markdown compare BASELINE.json CANDIDATE.json` rather than copying values by hand. The record carries the dataset and configuration identity and the baseline-policy caveats, shows each attempt's stopping gate instead of its free-text reason, and keeps unknown usage `unknown`. Add what the report cannot know yourself: the code revision, image digest, runtime, model route and which Docker, Temporal or live gates were unrun.

## Recording a live run in one step

`just live-agent ROLE DATASET [BASELINE]` and `just live-chain DATASET [BASELINE]` run the same evaluators as `eval-agent` and `eval` and leave a uniform record. Both read `.state/settings.json` (create it with `just settings-init`) and refuse, with exit `2` and before any model call, when:

- the file is missing or does not name `models.connector`, or the role's model is unset;
- the provider environment for that connector is absent from this shell: for `gemini`, `GOOGLE_API_KEY`, `GEMINI_API_KEY`, or `GOOGLE_GENAI_USE_VERTEXAI` with `GOOGLE_CLOUD_PROJECT`; for `litellm`, the route's key (`openai/`, `anthropic/`, `gemini/`), or `models.api_base` for `hosted_vllm/`. Name the variables of any other route with `--require-env NAME`. Only variable names are printed, never values;
- the dataset is not of the recipe's kind, or the baseline is a report of another role or kind, or covers another dataset digest (which `corsair compare` would refuse after the model was spent). `--allow-dataset-mismatch` records a mismatched comparison instead;
- for `live-chain`, `corsair doctor` is not ready, so start Temporal and a worker first (`just temporal-up worker-up` from the shell that holds the provider environment, since the worker reads it, not this check).

`--dry-run` performs every check above except `doctor`, prints the plan (connector, model names, provider variable names, dataset digest, record directory and the exact commands) and runs nothing. `--repeats N` defaults to 3 and `live-chain --concurrency N` to 1.

Each run writes an ignored `.runs/live/<UTC stamp>-<kind>-<dataset>/` holding the raw `report.json`, a sanitised `identity.json` (commit, tree and dirty flag; settings-file sha256 and the rows' config digests; connector and model names, whether an endpoint is configured but not the endpoint; image name and id; dataset path and digest; per-agent resource digests from the rows; repeats), `comparison.json` from `corsair --format json compare` when a baseline is given, and a `README.md` draft rendered from the report: identity and results tables, one row per case with its labels, unknown usage kept unknown, failure stops, the comparison and a list of what the record does not exercise (for an agent run: Docker, Temporal, the kernel and the other role; for a chain run: each decisive label no row reached, each ledger stage no round reached, and a second session that never started). It exits `1` when the comparison found a regression and `0` otherwise; failed rows are results, not a recipe failure. The draft marks its open items `TODO`. A human reviews it and the report before anything is copied under [`evals/baselines/candidates/`](../../evals/baselines/candidates/README.md); the recipe never writes there and promotes nothing.

## Families and splits

A family is one vulnerability class in one target: both variants of a chain pair and any adversarial row built on them. Promotion needs family-grouped held-out data, so a family must appear in exactly one split. `just dataset-families` checks every manifest under `evals/datasets/` (or the manifests given) and exits `1` when a family, a case or a chain pair crosses splits, or when a pair's variants carry different families; [`evaluation/families.py`](../../src/corsair/evaluation/families.py) exposes the same check as `check_family_splits(paths)` for a dataset validator. Composed report rows carry their `family` and `split`; `corsair report --families` adds per-family and per-split attempts, pass rate, decisive count, forbidden labels and operational failures, and `corsair compare --families` adds each family's deltas and attributed regressions. These views group already-scored rows and never re-score; a family's pass rate on a small frozen cohort is a diagnostic, not a class-level accuracy claim.

Use [the eval skill and coding-agent workflow](../development/coding-agent-workflows.md) for the concrete iteration sequence, and [extension qualification](../guides/extensions.md) before changing recipe, language, framework or image. Keep prior reports immutable and give each comparison a separate output path.
