# Native issue-analysis fixture composition qualification

This is the bounded priority 1A result in [SPEC-0015](../development/specs/SPEC-0015-native-issue-analysis-composition.md) and [PLAN-0017](../development/plans/PLAN-0017-native-issue-analysis-composition.md). ## Selected boundary

Python 3.12.13, PydanticAI 2.55.0 and Temporal Python SDK 1.34.0 ran against the verified Linux amd64 CLI 1.9.1 with embedded service 1.32.0. [Runtime pins](../../deploy/temporal/runtime-lock.yaml), `pyproject.toml` and `uv.lock` were frozen before execution. The binary SHA256 was rechecked as `712217694cac9f786a72d4b6c876cd15f3dcf1bf31434d9fed6af25242a327a0` before startup. The development service used exclusive loopback ports 17333/17334/17336, headless, with private SQLite and no cluster/container.

The source uses native `TemporalDurability`, `PydanticAIWorkflow`, `PydanticAIPlugin` and `LogfirePlugin`. A small workflow base accepts existing typed inputs, an admitted worker model key and a bounded request limit. The test-owned top-level concrete workflow registers exactly the same agent instance used directly. Registered fixture models/oracles stay in host-owned test configuration, outside agent prompts/dependencies. The workflow result contains only the typed analysis and primitive native usage counts. Native model/tool activities have bounded timeouts and maximum attempts one; output/tool retries are zero in this fixture configuration. There is no scheduler, opaque whole-agent activity, provider fallback or custom tracing protocol.

Research used Context7 discovery, the retained selected v2.55.0 integration documentation and installed selected-version source. The [immutable native documentation](https://github.com/pydantic/pydantic-ai/blob/v2.55.0/docs/durable_execution/temporal.md) and [implementation](https://github.com/pydantic/pydantic-ai/tree/v2.55.0/pydantic_ai_slim/pydantic_ai/durable_exec/temporal) define activity registration, typed conversion, replay and supported native instrumentation. The selected replay-safe tracing integration uses upstream experimental Temporal tracing; this report admits only the behavior actually observed with this pinned tuple.

## Coverage and limits

This proves the declared fixed fixture composition, authority/contract/limit failures, separate native model/tool execution, local native tracing and same-version history replay. It does not establish real model reasoning, provider retry/timeout semantics, OpenShell tool execution, complete investigation composition, crash/mid-activity recovery, production Temporal authentication/database durability, cross-version replay or application security remediation. The earlier independent [Temporal fixture report](temporal-fixture-foundation.md) has its own cancellation/retry/graceful restart envelope; those results are not silently extended to this agent slice.

The run recorded per-case native elapsed time in JUnit, direct/durable fixture usage, activity policies/counts, workflow/run/trace identities and native failure contexts. Hosted export, metrics, queue/backoff timing, internal RPC/poll retries, CPU/RSS and failure-run complete usage remain unknown. The listening metrics endpoint was not treated as metric qualification.
