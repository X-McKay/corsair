# Test authoring evaluation

Isolated [SPEC-0028](../../docs/development/specs/SPEC-0028-test-authoring-agent.md) stage. The agent receives a ready plan, the saved inventory and environment evidence; it writes tests only through `write_test_file` into approved paths and checks them with `run_tests`, whose security outcome is withheld by default.

The `development` set (`python/development/`, `sets/development.json`) holds nine cases built from the planner's reviewed reference plans: the SPEC-0018 realization, guarded source with the same patch, a collection error then fix, instruction injection in the saved baseline test, persistent collection errors up to the run budget, a failing control, and (SPEC-0043) a self-observing write refused then replaced, and refused twice, which ends blocked at admission, and the author reading its own written test after a collection error and then a path that is not in the source, answered typed (`unread_sources` counts those answers). Each input wraps the agent input with a `fixture_id` that selects the scripted runner and author; it never reaches the prompt. Metadata holds the scripted author's steps, the scripted runner's observations and the expected status, run count and assertion lines.

Evaluators report status, development run count, contract, security assertion lines, static semantics (Python AST: calls the planned target, no mocks, skips, swallowing excepts or constant asserts), read before write, write before run and withheld security separately, plus native budget and span checks. Positive target-call, security adversarial-literal and planned-assertion facts exclude nested functions, classes and lambdas. The negative control-literal check retains whole-function scanning, since helpers may run. The process fact covers listed imports and explicit os names through supported bindings; posix and indirect __dict__/vars access remain outside it. These checks do not resolve aliases, dataflow, branch reachability or safe-behavior semantics; independently reviewed sandbox replay remains necessary. No LLM judge is used.

Each development run is answered by the case's `runner_runs` entry (the last repeating once spent): an injected observation that puts the author in a condition, or `static`, the host runner in `static_runner.py` ([SPEC-0044](../../docs/development/specs/SPEC-0044-isolated-agent-evaluation.md)). It parses the patch and reports what collection could refuse (syntax errors, imports nothing could satisfy, node ids other than the planned pair) and, when exactly the pair is found, simulates execution as control passed and security failed, with run command `static-host-runner not-executed`. Nothing is executed on the host, so whether the tests run and discriminate the revisions stays unknown until a sandbox replay. `admission.py` adds facts scored in both modes: no process or network use, the plan's quoted adversarial input only in the security test, and plain asserts for a planned `AssertionError`.

```sh
make eval AGENT=authoring                                              # scripted author
make eval AGENT=authoring PROVIDER_CONFIG=<LocalModelConfig.json>      # live author, still host only
PYTHONPATH=src:. .venv/bin/python -m evals.test_authoring.evaluate --evidence .runs/test-authoring-<date>/fixture-001
```

Live mode drops the two checks that pin the scripted author's own run count and assertion lines, adds provider usage coverage, and records response ids and uncertain delivery in each receipt. Existing evidence directories are refused; every attempt keeps a receipt with `runner_sources` saying which runs were injected and which simulated.

## Native unit observation set

`make eval AGENT=authoring SET=unit` runs the frozen `unit` set (`python/unit/`). Both cases inject a recording database into the real query constructor, assert benign behavior and hostile input parameter binding, and require no database or recorder. The scripted author writes the reviewed native pair in `benchmarks/fixtures/sql-query-construction/test_queries.py`; the host port simulates its development run. Native execution of that pair is separately covered by `tests/agents/test_test_authoring.py`. These are development cases, not held-out semantic qualification. Copied targets, vacuity and misplaced security logic belong to the separate validity review evaluation; authoring's structural checks do not prove their absence.

Native assertion failure facts are operator data on `EnvironmentEvidence.assertion_facts`, populated from the selected framework table. Shared authoring guidance consumes these facts without framework recipes. Existing fixture cases and legacy evaluation bytes remain unchanged.

## Breadth set

`make eval AGENT=authoring SET=breadth` runs the frozen per-case set `sets/breadth.json` (cases under `<language>/breadth/<case id>/`, layout in `evals/cases.py`; `dataset_sha256` is the set digest). It holds ten Ruby (Minitest) cases over seven synthetic families with unit-contract plans (observation kinds, no witness): the reference realisation passing its first run, guarded source with the same patch, a collection error then fix, a load error persisting to the run budget (blocked at discovery), a failing control (blocked at fixture), instructions injected into the saved baseline test, the author reading its own file and a path not in the source after a run that did not discover the planned id, a `dependency_call` plan with an injected recording double, an `exception` plan (`assert_raises`) and a `fixture_state` plan over a temporary directory. Each oracle carries its own named test files (`files`), which the scripted author writes in place of the shared `FILES`.

Checks dispatch on the planned test id's grammar (`languages.py`); Python ids keep the AST path above unchanged. For Minitest and Jest, `parses_and_defines_test` and `has_assertion` come from the production readers the stage finalizes with (`static.assertion_lines`), and the rest are documented lexical patterns over the test body: the plan's callee expression called, no skip, no constant assertion, no process or network use, the quoted adversarial literal only in the security body, and the planned assertion lines when the plan's failure type is the framework's assertion error (`Minitest::Assertion`, Jest's `Error`). `no_mock` and swallowing checks stay Python-only, and `stage_admitted` is omitted because the stage's own admission check parses Python only and admits every other file unread. The static host runner discovers Minitest and Jest files the same way (ids through the production readers plus a lexical scan for other test definitions; a file the reader cannot parse, an unresolved `require` or ids other than the planned pair are a collection error) and simulates the security failure with that framework's native assertion type; JUnit and TAP files are refused there and their cases use injected observations.

`sets/breadth_pending.json` (cases under `<language>/breadth_pending/`) holds the same ten behaviours for JavaScript (Jest), Java (JUnit 5) and Perl (TAP), case kind `pending-reader`, each `case.json` naming the missing production piece. Today `TestAuthoringInput` admits pytest and Minitest ids only, so every pending case is refused as input; Java and Perl patch cases also need an assertion reader (draft PR #128 adds the Perl id grammar and reader). `PYTHONPATH=src:. .venv/bin/python -m evals.test_authoring.evaluate --cases breadth_pending --evidence <new dir>` runs them case by case, writes `pending.json` and fails until that support lands; `tests/configuration/test_breadth_authoring.py` pins the one refusal reason per case.
