# Matched split-authoring pilot

This eval-only experiment compares one call drafting a control/exploit pair with two sequential calls through the same factory: control, then exploit. The exploit call receives the admitted control file as immutable readable input. Both variants use exactly the same frozen property, source, environment, separate approved paths and operator-resolved native test identities. The two original SQL authoring fixtures remain unchanged; `cases-v1.json` projects their existing property intent and changes both variants' approved paths/IDs to distinct files. Case names, scripted answers, rubric and future execution outcomes are not model inputs.

`manifest-v1.json` freezes the pilot cases, independently declared `rubric-v1.json`, scripted plumbing patches and original dataset identity before live runs. The primary result is independently reviewed valid pairs with both native probe outcomes. Draft completion is recorded separately and never counted as semantic validity, test discovery, native execution or a fix verdict. That primary metric stays null until separate review and authorized execution. This two-case pilot does not qualify transfer across languages, frameworks or CWEs.

```sh
PYTHONPATH=src:. .venv/bin/python -m evals.experiments.split_authoring.evaluate --variant pair --repeat 1 --evidence .runs/split-pilot-pair
PYTHONPATH=src:. .venv/bin/python -m evals.experiments.split_authoring.evaluate --variant split --repeat 1 --evidence .runs/split-pilot-split
```

Omitting `--provider-config` runs fixed scripted native SDK plumbing only. Supplying an explicit authoring provider configuration selects that model exclusively. `--variant both` runs both variants serially. No task retries or parallel inference occur. The same cumulative native `RunUsage` and limits apply across calls in each attempt: 10 requests, 9 tool calls, 128,000 total tokens and one 900-second deadline. Stage two does not run after blocked or failed control. Split stages have fresh message histories; the frozen control is explicit data, not fabricated tool history. Additional split prompt/input overhead counts toward the same budget.

Each `<case>/<repeat>/<variant>/receipt.json` preserves stage inputs, prompt/schema/source/skill/tool identities, native messages, cumulative usage before/after, duration, failures and draft outputs. Adjacent `output.json` contains assembled files and their standard `ApprovedPatch` digest for independent review/execution. `configuration.json` pins the input/rubric manifest, factory, runner and provider configuration; `report.json` links receipts and outputs. Scripted token values are SDK estimates; live missing provider usage is unknown, not zero. Old evaluator results are not rewritten.

The harness never executes generated code, launches containers or supplies variant outcomes to drafting. Separate outcome-blind pair review must establish production binding and assertion relevance; separate native execution must run exactly the control and exploit probes. Parent-owned `native.py` is a later sandbox calibration helper, not part of drafting or its prompts. Failed control or an invalid pair cannot establish a security conclusion.

An admitted control may exceed the exploit stage's bounded source-read inventory. That failure is recorded as `handoff_admission`, with the completed control artifact and rejected next input retained and no exploit model call. Later cases/variants continue. This is a harness admission limitation, not a semantic invalid-pair judgment or an agent failure. Unknown variants are rejected before output creation.

## Tailored comparison v2

The first pilot measured separate contexts with shared guidance. It did not establish whether independently tailored control and exploit specialists are preferable. V2 provides separate `draft-control` and `draft-exploit` native capability skills. Each split role receives only its specialist section plus the shared foundation; the joint role receives the exact union. Agents have distinct names, fresh contexts and enforced file ownership. Exploit receives the frozen control artifact without its author's reasoning.

`cases-v2.json` changes only the shared property wording to clearly distinguish stable benign behavior from adversarial security. Both arms receive identical v2 inputs. Guidance and task wording both changed from v1; any v1-to-v2 improvement cannot be attributed exclusively to specialization. The historical v1 cases/manifests and run snapshots remain intact. `--guidance legacy` selects old cases/shared skill for plumbing comparison; exact historical replay uses the retained frozen v1 source rather than the evolved runner.

Run `--guidance tailored --variant both --repeat 3` for six matched comparisons (two related source cases, three repeats). Order alternates by case and repetition, giving three starts per arm. Cumulative budgets/provider settings are unchanged. Separate split output-retry opportunities are part of decomposition and count against the total budget. No outcome feedback or semantic repair occurs during drafting.

Receipts retain the complete specialist skill content and hashes. Independent source-only review binds the approved patch and every captured source file before native execution. The existing offline Docker fixture stages the complete source inventory, including the existing test module. Exactly the same control and exploit are discovered and executed on each captured revision; per-probe outcomes and cleanup are retained. Supported source review alone does not establish native execution, and invalid/unsupported pairs cannot produce application conclusions.
